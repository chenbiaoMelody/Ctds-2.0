## 2. 分项对策：表现 → 根因 → 规避 → 检测

### R1 上下文丢失/腐化（Context Loss & Rot）

- **表现**：会话越长 AI 越健忘；前面纠正过的问题后面再犯；忽略既有模块直接重造轮子。
- **根因**：上下文窗口是边际收益递减的有限资源（Anthropic 上下文工程研究）；长会话中注意力被稀释，早期约定被"挤出"。
- **规避策略**：
  1. **任务拆小**：单个 AI 会话只做一个 PRD 条目或一个明确任务（理想规模：一次可评审的 PR）。
  2. **规则文件承载稳定约束**：`AGENTS.md` + `docs/adr/`（架构决策记录）让 AI 每次开局自动获得项目约定，不依赖会话记忆。
  3. **会话卫生铁律**：同一问题纠正两次仍未解决 → 立即重开会话，把教训写进任务描述或规则文件，而不是继续纠缠（Anthropic 实证："干净的会话 + 更好的提示"几乎总是更优）。
  4. **50% 停机规则**（章程 V2.3 强制）：会话上下文用量达 50% 即完成当前最小步骤停机——上下文越满模型表现越差，而压缩又会不可控地丢失关键细节，两者都比"停机重启"更危险；禁止以自动/手动压缩延续任务。
  5. **开发日志续点落盘**（强制）：每次会话结束前在 `docs/logs/` **新建一份** `Ctds-项目开发日志-yy-mm-dd-hhss.md`（一任务一份、一次成文，禁止在旧日志上增量追加；历史日志只读），续点四要素（已完成/下一步/关键决策/文件指针）缺一不可；新会话一律读最新日志与 `AGENTS.md` 冷启动，禁止凭旧会话记忆（聊天截图/口头转述）续任务。
  6. **结构化笔记外部化**：跨会话任务用 `docs/tasks/<需求编号>.md` 记录决策、进度、未解决问题，新会话先读它。
  7. **探索隔离**：大范围代码调研交给子智能体/独立会话，只把结论（而非过程）带回主会话。
- **检测手段**：
  - 会话自查清单：开始编码前 AI 必须复述"本任务对应的 PRD 编号、涉及的既有模块、必须遵守的约定"，由人确认无误再动手。
  - 会话纪律巡检：抽查开发日志完整性（命名规范、续点四要素、与仓库实际状态一致）与 50% 停机执行情况；日志缺失或续点不合格视为流程违规。
  - PR 评审时检查"是否引用了本应使用的既有组件/工具类"（绕过即上下文丢失的症状）。
  - CI 门禁：模块依赖检查（如 archunit/dependency-cruiser）防止 AI 重建已有基础设施。

### R2 代码一致性破坏（Consistency）

- **表现**：同一个分页、鉴权、错误码逻辑出现 N 种实现；命名风格漂移；目录结构被 AI"创新"。
- **根因**：模型对仓库惯例的遵守依赖显式提供；AI 倾向生成训练数据中最常见的写法而非本仓库的写法。
- **规避策略**：
  1. **规范可执行化**：Formatter + Linter（后端 Checkstyle/Spotless、前端 ESLint/Prettier）+ 提交钩子强制执行，规范不靠自觉。
  2. **公共组件库优先原则**（写入 AGENTS.md）：AI 实现功能前必须先检索"是否已有等价实现"；统一在 `common/core` 模块沉淀分页、鉴权、错误码、日志、加解密等横切能力。
  3. **架构约束显式化**：分层规则（如 Controller 不得直接访问 DAO）、模块依赖方向用静态检查固化。
  4. **新代码必须在 PR 描述中声明"复用了哪些既有组件"**，评审人核验。
- **检测手段**：
  - CI 强制 lint/format 门禁（不通过即拒绝合并）。
  - 重复度扫描（jscpd / PMD CPD）：新增重复代码超阈值（建议：5+ 行重复块占比 <3%）告警（依据 GitClear 2025 数据，AI 项目重复率会快速恶化）。
  - 评审清单必查项："是否与相邻代码风格一致？是否重复实现了已有能力？"

### R3 需求漂移与范围蔓延（Requirement Drift / Scope Creep）

- **表现**：AI 按"合理想象"补全需求；实现的功能 PRD 里没有；口径与 PRD 验收标准不一致；越做越大。
- **根因**：AI 以"看起来合理"为目标而非"符合规格"；需求口头化、碎片化传递。
- **规避策略**：
  1. **规格先行**：每个开发条目先建 `docs/specs/<需求编号>.md`，内容为：对应 PRD 编号（如 C-4.3）、验收标准（Given/When/Then）、边界与非目标（明确写"不做"）。规格未评审不开工。
  2. **需求编号贯穿**：分支名、commit、PR、测试用例全部携带 PRD 编号（如 `feat/C-4.3-policy-engine`），实现全程可追溯。
  3. **YAGNI 硬约束**（写入 AGENTS.md）：只实现规格中明确列出的行为；AI 认为需要补充的能力必须以"建议"形式列在 PR 描述，不得直接实现。
  4. **变更先改规格**：需求变化时先更新规格文件并走变更流程（章程第 7 章），再改代码；禁止"边聊边改"。
- **检测手段**：
  - PR 模板强制包含"对应需求编号 + 验收标准对照表"。
  - AI 对抗性预审：新鲜上下文的评审智能体只看"规格 + diff"，回答"哪些改动超出规格范围、哪些规格点未实现"。
  - 月度追溯审计：抽查需求编号，核对 PRD → 规格 → 代码 → 测试四层一致性。

### R4 技术债务累积（Tech Debt）

- **表现**：TODO/FIXME 堆积；"先跑通再说"的临时代码进入主干；重复代码；重构永远排不上。
- **根因**：AI 追求"完成任务"而非"可维护"；速度优先文化下 DoD（完成定义）被侵蚀；GitClear 数据显示 AI 显著加剧复制粘贴式膨胀。
- **规避策略**：
  1. **DoD 强制门禁**：定义"完成 = 测试通过 + lint 通过 + 文档更新 + 无新增 TODO"。TODO 进入主干需在 issue 系统登记编号并注明计划迭代。
  2. **债务登记簿**：`docs/debt-register.md` 记录已知债务（位置、影响、利息、偿还计划），月度评审。
  3. **重构预算**：每个迭代固定预留 15%–20% 工时/算力用于重构与偿还债务（含"AI 产出重构"）。
  4. **禁止无主死代码**：删除而非注释保留；AI 生成后废弃的代码必须随 PR 清理。
- **检测手段**：
  - CI 指标趋势：新增代码 vs 删除/移动代码比率、重复度、圈复杂度（PMD/SonarQube）、TODO 计数——任一指标连续两个迭代恶化即触发专项治理。
  - SonarQube 质量门禁：新代码异味/坏味道阈值（如新增阻塞级问题 = 0）。
  - 季度"债务周"：集中偿还登记簿中高利息项。

### R5 测试覆盖不足（Test Coverage）

- **表现**：覆盖率达标但断言空洞（`assert true`、只测 happy path）；AI 写的测试与实现"同源同错"；集成/边界场景缺失。
- **根因**：AI 自写自测时倾向于让测试迁就实现（包括迁就错误实现）；人类又因信任自动化而放松审查。
- **规避策略**：
  1. **测试先行（TDD）**：规格评审通过后先写测试（人或独立 AI 会话），实现以"让测试通过"为目标；**写测试与写实现分离**（Writer/Reviewer 模式），防止同源错误。
  2. **验收标准直译测试**：规格中的 Given/When/Then 必须一一映射到测试用例，评审时核对映射表。
  3. **测试质量审查由机器与 AI 承担**（V1.1：人不具备审查测试代码的能力）：变异测试验证测试有效性；独立测试审计智能体（新鲜上下文）核查断言有效性、异常路径覆盖、与验收标准的映射完整性；人工只核对"验收剧本可执行、可观察"。
  4. **分层测试策略**：单元（快、多）→ 契约（API/连接器接口）→ 集成（数据库/消息/网关）→ E2E（核心流程，如上架-订购-交付-计量）。
  5. **高价值场景强制专项**：使用控制策略引擎（C-4.3）的每个策略必须有"策略生效 + 策略绕过失败"的双向用例；计费分账（C-7.2/7.3）必须有对账型断言。
- **检测手段**：
  - 覆盖率门禁：行覆盖率整体 ≥70%，核心模块（合约引擎、计量计费、加解密、权限）≥80%，且**分支覆盖率**一并统计；仅行覆盖率视为未达标。
  - 变异测试（核心模块必做、普通模块抽检）：变异杀除率 <60% 的模块列入测试加固计划——这是无人工测试审查条件下测试有效性的主要机器判据。
  - 独立测试审计智能体（新鲜上下文）逐 PR 评估测试质量：断言是否具体、异常路径是否覆盖、是否与验收标准一一映射。
  - 随机"红队测试会话"：让 AI 专门尝试构造让代码出错的输入（对抗性测试），产出纳入回归集。

### R6 AI 生成错误/低效代码（Wrong / Inefficient Code）

- **表现**：幻觉不存在的 API/配置项；O(n²) 处理本应 O(n) 的数据；编造业务规则；并发/事务处理错误。
- **根因**：模型概率生成而非"查证"生成；对项目内自定义 API 与领域规则（如国密、DID 协议）无真知。
- **规避策略**：
  1. **编译与类型即检测**：强类型语言 + 严格编译告警，幻觉 API 大部分在此被拦截；类型检查进本地与 CI 双重门禁。
  2. **领域知识供给**：关键协议/规则（国密 SM2/SM4 用法、DID 规范、信通院接口约定、等保要求）整理为 `docs/domain/` 参考文档并在任务中显式引用，减少 AI 臆测。
  3. **关键路径人工实现或人工精审**：加解密、密钥管理、策略引擎、分布式事务、资金相关（计费分账）代码由资深工程师主导，AI 辅助。
  4. **性能敏感点白名单**：API 网关、目录检索、计量流水写入等高性能路径（对应 PRD 性能指标）实现后必须跑基准测试（JMH/wrk）再合并。
  5. **AI 建议的算法需声明复杂度与数据规模假设**，由评审智能体（正确性视角）验证（V1.1：人不承担此项）。
- **检测手段**：
  - 静态分析（SonarQube、Semgrep）+ AI 评审会审双通道。
  - 评审智能体必查项：外部调用是否真实存在（以编译与类型检查为准）、循环内是否有 IO/远程调用、事务与锁边界。
  - 未通过编译/测试前不进入 AI 评审会审（评审算力不浪费在明显错误上）。

### R7 安全与供应链风险（Security & Supply Chain）

- **表现**：AI 幻觉出不存在的包名（攻击者抢注 = slopsquatting）；引入有漏洞的依赖版本；硬编码密钥/口令；SQL 注入、反序列化等漏洞被 AI 复制；日志打印敏感数据。
- **根因**：AI 无实时包注册表校验；训练数据含漏洞代码；生成效率优先于安全默认值。约四成 AI 生成代码片段被发现含安全缺陷的行业研究结论应作为底线假设。
- **规避策略**：
  1. **依赖三重门**：① 白名单 + 锁定文件（lockfile）管理依赖；② 新依赖必须人工审批并登记（含许可证审查）；③ CI 强制 SCA 扫描（Dependency-Check/Snyk 类）。**禁止直接安装 AI 建议的未经验证的包名**（写入 AGENTS.md 红线）。
  2. **密钥零入库**：密钥只进 KMS/环境配置中心；pre-commit 扫描（gitleaks/trufflehog）拦截。
  3. **安全编码基线**：输入校验、参数化查询、最小权限、安全日志（脱敏）写入 AGENTS.md；本项目为等保三级，加解密一律走封装好的国密组件（SM2/SM4），**禁止 AI 自行实现密码学算法**。
  4. **SAST 进流水线**：SonarQube 安全热点 + Semgrep 规则集（含 OWASP Top 10）；安全热点清零才可发布。
- **检测手段**：
  - CI 三扫描门禁：SCA（漏洞+许可证）、SAST、secrets 扫描；阻断级 = 拒绝合并。
  - 上线前渗透测试 + 等保三级测评（外部机构）。
  - SBOM（软件物料清单）随版本产出，供客户安全审查（政务交付常见要求）。

### R8 数据合规风险（Data Compliance）

- **表现**：源码、PRD、客户数据被上传到不受控的公有云 AI 服务；AI 缓存/训练策略未知。
- **根因**：工具选型未做数据流向评估；开发者图方便使用个人账号工具。
- **规避策略**：
  1. **工具白名单制度**：仅允许使用经安全合规评估的 AI 工具（企业级合约，含数据不用于训练条款）；个人账号工具禁用于项目资产。
  2. **分级输入策略**：客户真实数据、生产凭证、个人信息一律不得作为 AI 输入；脱敏后的样例数据方可使用。
  3. **权限最小化**：AI 智能体的仓库/系统权限按任务授予并定期回收；无人值守任务使用受限权限白名单。
- **检测手段**：季度工具使用审计；出网/代理日志审计（政务内网环境）；新人准入培训含数据红线考试。

### R9 过度工程（Over-engineering）

- **表现**：AI 主动引入无需求的抽象层、重试框架、插件机制、多余配置项；防御性代码淹没业务逻辑。
- **根因**：模型对"好工程"的先验偏向完备性；任务描述未限定范围。
- **规避策略**：
  1. YAGNI 原则写入 AGENTS.md："做最简单有效的事"；规格写明非目标。
  2. PR 描述要求 AI 列出"超出规格的实现"（有则说明理由或移除）。
- **检测手段**：评审时对照规格 diff；新增依赖/新框架必须说明不可替代理由（对应依赖审批流程）。

### R10 责任模糊（Accountability Diffusion）

- **表现**："AI 写的"成为免责借口；功能无人对业务行为负责；缺陷追溯时推诿。
- **根因**：无编程团队下"代码级作者理解"不可得，V1.0 的"提交者负全责、答不出即退回"机制失效。
- **规避策略**（V1.1 重构为双层责任）：
  1. **双层责任**：AI 编排师对"提交内容与规格一致、流程合规、业务验收通过"负全责；代码正确性与技术质量由编码智能体、AI 评审会审与自动门禁承担（对外责任由项目整体承担，残余风险见章程 4.5 声明）。
  2. **演示答辩制**：合并前提交人（编排师）须能按验收剧本完整演示功能，并回答业务性问题（"这个场景下系统会怎样"）；答不出业务行为即退回——保证主干功能有人懂，替代 V1.0 的代码问答。
  3. **AI 参与标记**：PR 模板声明 AI 参与程度（辅助补全/主体生成），便于质量分析与追溯，不用于免责。
  4. **业务可读交付说明**：每个 PR 附非程序员可读的"改了什么功能、如何演示"，作为责任载体。
- **检测手段**：演示答辩抽查（随机功能由提交人现场演示并答业务问题）；交付说明与实际演示一致性抽查；外部顾问审计时核对责任链记录。

### R11 工具/模型依赖风险（Tool & Vendor Risk）

- **表现**：模型服务限流/停服阻塞交付；工具升级改变行为导致既有流程失效；提示词/规则失效。
- **规避策略**：
  1. 关键流程不绑死单一模型：规格、测试、ADR 等知识资产对模型中立（Markdown 存储），可随时切换工具。
  2. 主模型 + 备用模型双轨备案；AI 服务不可用时降级为人工开发流程（章程第 8 章应急预案）。
  3. 模型/工具版本变更视为"环境变更"：变更后先跑回归评测（用项目保留的基准任务集）再全面使用。
- **检测手段**：月度记录各任务 AI 使用效率基线，异常劣化即触发评测。

### R12 知识腐化/文档漂移（Knowledge Decay）

- **表现**：ADR 与实际实现不一致；规则文件过期误导 AI；新人接手成本失控。
- **规避策略**：
  1. **文档随代码走**：架构变更 PR 必须同步更新 ADR 与模块 README（DoD 项）。
  2. ADR 记录"决策 + 理由 + 备选项"，AI 实现前引用，避免重新发明或违背。
- **检测手段**：月度一致性抽查：抽 3 个 ADR 对照代码；CI 检查规则文件引用的路径/命令是否仍有效。

### R13 系统性能力缺口（全员无编程经验，V1.1 新增）

- **表现**：架构决策、代码评审、测试设计、安全设计、缺陷定位全部无人类兜底；AI 生成链与自动门禁成为技术质量唯一守门人；多个评审智能体可能共享同类盲区（同源模型偏差），盲区叠加无人发现。
- **根因**：团队构成约束（章程 V2.0 确立）。这是本项目的系统性风险，不是单点缺陷。
- **规避策略**：
  1. **技术栈平庸化**（章程 4.1）：只用 AI 最熟悉、生态最成熟的主流技术，降低生成缺陷率、提高外部可接手性；
  2. **门禁无特批**：杜绝"例外"——无人能评估例外风险，所以例外通道一律不设；
  3. **AI 评审会审异构化**：4 个评审视角使用相互独立的会话（有条件时使用不同模型），降低同源盲区叠加；
  4. **外部技术顾问兜底**：M2/M3 里程碑各一次技术审计（2–3 人日），重大架构决策外部复核，S0 应急支持通道 48h 内响应（章程 2.2 强烈建议，列入预算）；
  5. **可接手性建设**：追溯矩阵 + ADR + 业务可读系统说明书完整维护，确保未来任何时点引入人类工程师的成本可控。
- **检测手段**：里程碑外部审计问题数趋势（连续下降为健康）；门禁绕过尝试审计（应为 0）；评审会审"全绿但演示失败"事件计数（连续 ≥2 次触发流程复盘）；文档可接手性抽检（外部视角随机认读）。

## 3. 风险巡检机制（落地节奏）

| 节奏 | 动作 | 责任人 |
| --- | --- | --- |
| 每次提交 | lint/类型/测试/secrets 扫描/SCA 自动门禁 | CI |
| 每次会话结束 | 开发日志落盘检查（命名 `Ctds-项目开发日志-yy-mm-dd-hhss`、续点四要素齐备） | AI编排师 |
| 每个 PR | AI 评审会审（4 视角独立会话）+ 编排师核对单 + 业务验收剧本 | 编排师/业务验收员 |
| 每周 | 质量指标看板：覆盖率、变异杀除率、重复度、TODO 数、变更失败率 | AI编排负责人 |
| 每迭代 | 债务登记簿评审 + 追溯抽查（需求编号多层一致性）+ 演示会 | 产品负责人 |
| 每月 | ADR 一致性抽查、工具与模型基线评测、合规审计 | 安全合规专员+运维专员 |
| 每季度 | 渗透测试/等保自查、风险登记册全面刷新、流程复盘 | 项目经理 |
| 每里程碑 | **外部技术顾问审计**（代码级质量兜底，M2/M3 必做） | 项目经理 |

> 风险登记册（R1–R13 + 项目特有风险）在章程第 8 章纳入统一管理；本手册提供逐项操作细则。
