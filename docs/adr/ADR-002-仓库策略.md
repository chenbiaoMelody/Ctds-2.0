## 1. 背景

平台含 10+ 后端微服务、前端、连接器 SDK、公共组件（common）、标准适配层（std-adapter）、部署脚本与全套文档；AI 多智能体并行开发需要明确的代码归属边界与依赖规则。

## 2. 备选方案对比

| 维度 | 方案 A：monorepo 为主（推荐） | 方案 B：按服务全分仓 |
| --- | --- | --- |
| 跨模块重构/原子提交 | 一次提交贯穿多模块 | 需跨仓协调，AI 易漏改 |
| 公共组件（common）复用 | 同仓直接引用，门禁可查 | 需发版流程，1 人团队负担重 |
| 连接器 SDK 独立分发 | 需单独建仓（见决策） | 天然独立 |
| AI 并行任务隔离 | 依赖 WBS 模块边界 + 独立分支 | 物理隔离更强 |
| 门禁全量运行成本 | 全量构建较慢（可按模块增量） | 单仓快 |

## 3. 决策（推荐）

1. **monorepo**：平台各微服务、前端、common、std-adapter、部署脚本、文档同仓（`Ctds-2.0`）；模块目录规划：`services/<服务名>`、`frontend/`、`common/`、`std-adapter/`、`connector-sdk/`、`deploy/`、`docs/`、`scripts/`。
2. **连接器 SDK 分仓**：需要对外独立分发版本时单独建仓并版本化发布（章程 5.x 预留，V1.0 期间在 monorepo 内开发）。
3. **分支模型**：`main`（保护，仅经合并进入）+ `feat/<编号>-短描述` / `fix/<编号>-短描述`（短生命周期）+ `release/*`（里程碑冻结期）。
4. **分支保护方案**：禁止直推 `main`/`release/*`；合并前必须门禁全绿 + 4 视角评审通过 + PO 业务批准（三道防线）。当前无远程托管（GitHub 直连不通、零预算），过渡措施：本地裸仓库作 `origin` 做备份与推送演练，保护规则以文档形式先行生效（自检单第 6 项人工核对提交记录）；远程托管落地后（Gitee 私有免费或自建 Gitea，另行走变更流程）立即启用平台级分支保护。

## 4. 理由与业务影响说明

**理由**：1 人团队 + AI 多智能体并行开发的最大成本是"跨仓协调"——monorepo 让跨模块原子提交、公共组件同仓复用、门禁全量检查都成为默认能力；全分仓的发版/依赖升级流程对 1 人团队不成比例。连接器 SDK 分仓保留在真正需要对外分发时执行（YAGNI）。

- **成本**：零（本地裸仓与未来 Gitee 私有仓均免费）；
- **工期**：monorepo 减少 1 人团队的发版协调成本；
- **风险**：无远程异地备份期间，机器故障=资产全损——过渡期以本地裸仓 + 定期压缩备份到另一磁盘缓解，远程托管列为基建待办；
- **影响范围**：全仓库工作流。

## 5. 可替换性评估（D-3）

monorepo 结构是 git 原生形态，与托管平台无关；迁移到任何远程托管只需改 remote 地址。风险等级：低。
