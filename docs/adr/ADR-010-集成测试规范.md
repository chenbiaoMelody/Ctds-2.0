## 1. 背景

集成测试要验证"代码 + 真实中间件"协作正确（迁移真跑在 MySQL 8 上、端点真读写真库）。2.4.7 确立"真实中间件在配了它的环境跑"原则、2.4.10 以环境变量门控 + 人工 Docker 演练承接——但默认门禁环境下集成测试永远跳过（覆盖缺口，2.4.10 评审③指认并接受），护栏场景（乱序拒绝、篡改 fail-fast）靠人工演练无法进 `mvn test` 自动回归。WBS 2.4.11 产出定义"Testcontainers 集成测试框架 + 示例"，本 ADR 固化容器化集成测试的平台级规范。

## 2. 备选方案与取舍

| 备选 | 取舍结论 |
| --- | --- |
| **Testcontainers（选定）** | Java 测试生态事实标准、Spring Boot 官方文档标准方案（spring-boot-testcontainers + @ServiceConnection）、测试时自动起一次性真实容器测后自动销毁。取舍：需要本机 Docker 运行（以"无 Docker 自动跳过"承接，门禁不红） |
| 维持环境变量门控 + 人工演练 | 现状即此，自动化缺口不补（2.4.10 评审③指认），护栏场景无法自动回归。**不采用**（升级为容器化） |
| H2 等内存数据库替代真实库 | 不是真实 MySQL：方言/迁移/锁行为失真，违背"真实中间件"原则（2.4.10 已拒过同一备选）。**禁止** |
| 共享测试基座 common 模块 | 当前仅 example-service 一个消费者，属过度设计（沿 2.4.10"不建 common-migration"同口径）。**暂不建**（沉淀条件见 §3.6） |

## 3. 决策（规范正文）

1. **框架**：Testcontainers（`org.testcontainers:junit-jupiter` + 中间件模块如 `org.testcontainers:mysql` + `org.springframework.boot:spring-boot-testcontainers`，版本由 Spring Boot BOM 统一管理，dependencies.md 登记）；**全部 test scope**，禁止进入业务制品（compile/runtime 作用域不得出现）；
2. **容器声明**：`@Testcontainers(disabledWithoutDocker = true)` 类注解 + `@Container` 静态字段（类级共享容器）+ Spring 场景加 `@ServiceConnection` 自动注入连接参数；**镜像必须显式标签**（如 `mysql:8.0`），禁止 `latest`（可复现性）；镜像版本变更随 ADR-001 变更流程；
3. **命名与拾取**：容器化集成测试类名必须 `*Test` 结尾（surefire 默认拾取，2.4.10 教训：`*IT` 会在 `mvn test` 中静默消失形成假覆盖）；
4. **无 Docker 纪律**：本机 Docker 未运行时容器化用例自动跳过（`disabledWithoutDocker`），**门禁不红**；跳过态在 mvn 输出留痕；禁止为"让测试跑起来"而要求门禁环境必须起 Docker——有 Docker 时用例必须真实执行、无 Docker 时跳过，两态都合法；
5. **密钥零入库**：容器凭据由 Testcontainers 随机生成、仅存在于测试进程内存；代码/配置/日志不出现任何中间件口令（章程红线 7）；护栏类测试脚本写入临时目录，与生产脚本目录物理隔离；
6. **用例间数据库隔离**：同一测试类内多个用例若各自操作带状态中间件（如 Flyway history 表、业务表），且状态会相互污染（如版本号撞号），必须用**方法级容器**（非 static `@Container`）或各用例独立 schema/库名——不共享有状态库；只读/无状态用例可用类级容器共享（2.4.11 实测教训：两个护栏用例共享库导致 history 撞 V1 校验和）；
7. **共享基座沉淀条件**：≥2 个服务出现真实容器化集成测试消费者时，再评估提取共享测试基类/模块（届时走变更流程）；当前单消费者直接写在各服务测试源集；
8. **中间件客户端 API 使用范围**：测试源集允许使用中间件客户端 API 做行为断言（如 Flyway API 驱动迁移护栏用例，沿 ADR-009 §6）；main 源集禁用范围不因本 ADR 改变。

## 4. 理由与业务影响说明

- **业务影响**：原"人工 Docker 演练"验证的护栏场景（迁移乱序被拒、篡改 fail-fast、迁移幂等、端点真实读写）从一次性人工操作升级为每次 `mvn test` 自动回归——缺陷在合入前被机器拦截的概率上升，人工验收演示负担下降；
- **门禁稳定性**：无 Docker 环境自动跳过保证门禁在任意机器全绿（不因环境差异红灯），有 Docker 时自动升格为真实执行——自动化程度只升不降；
- **对无编程团队**：测试结果业务可读（"真实数据库上验证通过/跳过原因 = 本机没有 Docker"），不新增人工操作步骤。

## 5. 影响范围

- 全部含真实中间件集成测试的 services/（现 example-service 示例接入，后续业务服务遵循本规范）；
- 门禁：无新增门禁（容器化测试走既有 unitTest 阶段 `mvn test`，run-gates 配置零改动）；
- 环境要求（非门禁硬性）：真实执行需要本机 Docker；2.5.x 部署基建落地后，CI 环境的 Docker 供给随其评估；
- 观察项：① 门禁 coverage/mutationTest 阶段（PENDING）启用时，容器化测试的覆盖率统计口径随 2.2.x 工具链任务裁决；② 2.4.12 E2E 框架若需浏览器容器，沿本规范扩展。

## 6. 可替换性（组件级替换路径，防锁定）

- Testcontainers 为**可替换组件**而非平台契约：业务代码不依赖其 API（main 源集零依赖；测试源集的使用收敛于容器声明与断言，替换工具时仅测试源集受影响，业务代码零改动）；
- 替换路径：如未来切换其他容器化测试工具（如直接 Docker Compose + 环境变量注入），仅需重写测试源集的容器供给层，断言集与被测代码不变；
- 中间件本身的替换不在本 ADR 范围（ADR-001 冻结；国产化替代走 ADR-001 变更流程）。
