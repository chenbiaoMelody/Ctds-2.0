# ADR-014 监控告警基座规范（指标采集、基础看板、告警路由的组件选型与运行口径）

| 项 | 内容 |
| --- | --- |

| 关联任务 | WBS 2.5.3（本 ADR 为其规范载体）；消费方：WBS 3.9.4 监控运维集成、生产化部署任务 |
| 关联 ADR | ADR-001（技术栈冻结）、ADR-012（镜像命名）、ADR-013（部署模板与访问口径，本 ADR 的访问口径直接沿用其 §8.5） |

## 1. 背景

WBS 2.5.3 要求"指标采集、基础看板、告警路由"。ADR-013 §53 已明确"业务可用性监控在 2.5.3 做，探针只负责进程活着"的职责分离。开发/测试环境为单机 Docker Desktop 内置 Kubernetes（kind 模式）；本机网络直连 registry-1.docker.io 不通，镜像经 Docker Desktop 已配置加速器拉取。

## 2. 备选方案与取舍

- **部署形态**：朴素清单三件套（Prometheus + Alertmanager + Grafana 各 1 Deployment，选定）vs Helm kube-prometheus-stack（弃：需引入 Helm 新工具与新流程、十余 CRD、10+ Pod，单机内存吃紧，1 会话不可交付，且与 ADR-013 朴素清单路线分叉）vs Grafana 内置告警替代 Alertmanager（弃：告警路由被锁进 Grafana，生产对接通知渠道时需整体迁移，返工成本高）。
- **指标范围**：仅平台服务指标（选定）vs 加集群层（node-exporter/kube-state-metrics，弃：工作量翻倍超 1 会话，集群本身由 Docker Desktop 托管价值有限；登记为 3.9.4 或后续增强）。
- **告警触发"服务下线"**：`up == 0 or absent(up)`（选定，absent 保证副本缩 0/目标消失场景确定性触发）vs 仅 `up == 0`（弃：目标消失后序列变陈旧，规则不触发，演练不可重现）。
- **抓取发现**：Pod 注解（prometheus.io/scrape|port|path）+ kubernetes_sd relabel（选定，无 Operator/CRD 的 vanilla 主流做法）vs 静态 targets（弃：新服务接入要改 Prometheus 配置，注解方式新服务加注解即可）。注解发现需要最小 RBAC 配套（ServiceAccount + ClusterRole 只读 pods + 绑定；kind 模式集群默认开 RBAC，默认 ServiceAccount 无权 list pods——2.5.3 实测发现留痕），见 `deploy/k8s-monitoring/prometheus-rbac.yaml`。

## 3. 决策（规范正文）

### 3.1 组件与版本线（显式 tag，禁 latest）

| 组件 | 镜像与版本线 | 端口 | 存储口径 |
| --- | --- | --- | --- |
| ctds-prometheus | `prom/prometheus:v3.13.3`（3.x 当前 LTS；不追普通版 3.14，基座求稳） | 9090 | emptyDir，`--storage.tsdb.retention.time=24h`，抓取间隔 15s |
| ctds-alertmanager | `prom/alertmanager:v0.34.0`（GitHub Releases 最新稳定） | 9093 | emptyDir |
| ctds-grafana | `grafana/grafana:13.2.1`（当前稳定；AGPL-3.0 自部署使用） | 3000 | emptyDir（看板经 ConfigMap 预配，重建自愈） |

全部 1 副本、非 root（`runAsNonRoot`：prometheus/alertmanager uid 65534，grafana uid 472）、命名空间 `ctds-monitoring`。生产化任务的升级口径：持久化（PVC/对象存储）、高可用（多副本/多实例）、真实通知渠道。

### 3.2 指标暴露口径（平台服务）

- Spring Boot 服务以官方 `spring-boot-starter-actuator` + `io.micrometer:micrometer-registry-prometheus`（Boot BOM 托管，不显式锁版）暴露 `/actuator/prometheus`；暴露面收敛 `management.endpoints.web.exposure.include: health,prometheus`（最小暴露面，其余端点一律不开）。
- 鉴权零改动：common-auth 注解式按端点强制（无注解默认放行），禁止为指标端点新增鉴权逻辑或反向加白名单。
- 部署模板 Pod 注解三条：`prometheus.io/scrape: "true"` / `prometheus.io/port` / `prometheus.io/path: "/actuator/prometheus"`——新服务接入监控 = 复制这三条注解 + 引入两个 starter，零 Prometheus 配置改动。
- 测试口径：`@SpringBootTest` 默认禁用全部指标导出器（实测 simpleMeterRegistry 兜底、scrape 端点不装配），验证导出链路须 `@AutoConfigureObservability`；scrape 端点在 MOCK 环境不映射（实测 404 假阴性），用 `RANDOM_PORT` + `TestRestTemplate`。

### 3.3 告警规则口径（v1 两条）

| 规则 | 表达式要点 | for | 级别 |
| --- | --- | --- | --- |
| CtdsBackendDown | `up{job="ctds-backend"} == 0 or absent(up{job="ctds-backend"})` | 1m | critical |
| CtdsBackendHighErrorRate | 5 分钟窗口 5xx 占比 > 5%（总量为 0 时 NaN 不触发 = 安全侧） | 5m | warning |

`job` 标签由 Pod 标签 `app.kubernetes.io/name` relabel 而来；新增服务沿用同机制。新增规则须经任务卡与设计流程，不得擅自增删。

### 3.4 告警路由口径（v1）

默认路由 receiver `ctds-default`（空动作 receiver）：告警分组（group_by alertname）、静默、抑制能力可用，UI/API 可见；**真实对外发送**（邮件/出网 webhook）留生产任务扩展点。路由参数：group_wait 10s / group_interval 5m / repeat_interval 1h（开发环境短周期便于演示）。投递通道：Prometheus `alerting.alertmanagers` 静态指向集群内 `ctds-alertmanager:9093`（缺省不投递——2.5.3 实测留痕）。

### 3.5 看板口径（v1 一块基线看板）

Grafana 数据源与看板经 provisioning ConfigMap 全自动装载（零手工配置）；匿名 Viewer 免登录查看，admin 留镜像出厂默认（首次登录强制改密，**口令不落仓库**——生产化接配置中心）。看板《C-TDS 平台基础看板》四区块：服务存活 / JVM 堆内存与 GC / HTTP 速率 / 5xx 错误率与 P95 时延。

### 3.6 访问口径

沿用 ADR-013 §8.5：base 模板 ClusterIP；Grafana 经 NodePort 30082（脚本对**存活对象** patch，base 不改）+ 分离式 kubectl port-forward（脚本退出后存活，`-Teardown` 回收）；Prometheus/Alertmanager UI 不常驻，排查时手动转发（runbook 给命令）。

### 3.7 交付通道口径

独立 `scripts/deploy/monitoring.ps1`（不修改 2.5.2 已验证的 deploy.ps1）；监控栈生命周期独立于应用（可只拆监控不拆应用）。镜像装载沿用 2.5.2 实测口径：kind 模式集群不共享 docker 镜像，须 `docker save → 节点 ctr import`。脚本前提自检**不代部署应用**：检测到 default 命名空间无 ctds-backend 时提示先跑 deploy.ps1 并停止。报告落 `build-output/monitoring/<时间戳>/monitoring-report.md`，末行 `[MONITOR] PASS|FAIL`；Teardown 落 `build-output/monitoring/teardown-report.md`。

## 4. 边界（v1 明确不做）

开发/测试单机基线：数据存 Pod 本地盘（Pod 重建清零）、单副本无高可用、告警不对外发送、不含集群层指标。以上均为生产化任务（或 3.9.4）的登记扩展点，不是缺陷。

安全扩展点（评审②登记，生产化任务执行）：① Grafana 匿名 Viewer 可经 Explore 对数据源发任意 PromQL 读全平台指标——生产化须关闭 Explore 或关闭匿名访问；② 告警通知渠道接入后同步接入配置中心管理凭据；③ 镜像可升级为 digest 锁定（dependencies.md 已留完整 digest）。

脚本边界（评审②④登记）：恢复副本的安全网覆盖"脚本内失败"；脚本被 Ctrl+C/崩溃打断的窗口内后端可能停留在 0 副本，重跑 monitoring.ps1 或手动 `kubectl -n default scale deployment ctds-backend --replicas=1` 即恢复。

## 5. 后果

- 新服务接入监控的边际成本 = 2 个 BOM 依赖 + 3 行注解，无 Prometheus 侧改动；
- emptyDir 与 1 副本让 1 会话可交付，但意味着重启丢指标——验收口径是"链路可用"，不是"数据持久"；
- kind 模式镜像装载步骤是已知固有成本，随脚本自动化。
