## 1. 业务目标一句话

让“试图访问别人的资源”和“猜一个不存在的资源编号”尽可能难以靠响应耗时、后台审计负载或审计系统故障区分，同时保留越权行为可取证的能力。

## 2. 已核实事实

1. 三种业务路径都存在同一模式：资源存在且非属主时，先同步写一条拒绝留痕，再返回 400；资源不存在时，只查询后返回同样的 400。
2. 审计表没有拒绝业务唯一键；同一主体反复探测同一资源会持续新增记录。
3. 拒绝留痕写入失败会变成 500；不存在的请求仍是 400，因此故障时也能区分。
4. 网关已有“主体 + 接口”限流，但没有“主体 + 对象 + 动作”限流，直连服务也不受网关保护。
5. 公共异步审计不会阻塞请求，但允许丢事件；它适合补充安全审计，不能在不修改契约的情况下替代当前“拒绝必须留痕”的数据库记录。

## 3. 业务行为方案

### Q1-A：等强同步审计（AI 建议：审计要求严格时采用）

| 场景 | 请求处理 | 对外结果 | 内部留痕 |
| --- | --- | --- | --- |
| 首次访问存在但非属主的对象 | 完成对象级限流与去重判断，执行同一审计入口 | 400 + `1000C0003` + “资源不存在” | 记录一条拒绝审计 |
| 首次猜测不存在的对象 | 完成相同限流与去重判断，执行同一审计入口 | 与上一行逐字一致 | 记录一条拒绝审计，只含请求中的目标编号，不补造对象属性 |
| 窗口内重复同一主体 / 对象 / 动作 | 不重复写审计 | 仍为统一 400 | 保留窗口内首条 |
| 超过对象级探测阈值 | 在确定拒绝后、写审计前统一限流 | 429 + `Retry-After`，已知 / 未知对象一致 | 可按安全审计策略记录限流事件，不增加业务拒绝表写放大 |
| 审计入口故障 | 两态都经过同一入口 | 两态统一 500 + “系统繁忙，请稍后重试” | 业务拒绝未确认落库，故障进入运维告警 |

**保留边界**：对象查询本身仍有极小耗时差；本方案不承诺数学意义上的零侧信道。

### Q1-B：异步优先

- 两态都调用公共非阻塞审计入口，请求不等待数据库写入。
- 后台异步写审计表，业务页面从“立即可见”变为“最终可见”。
- 审计队列满、进程退出或后台写失败时可能延迟 / 丢失记录，以告警计数暴露。
- **闸门**：须先确认规格是否允许最终一致或有损审计；未批准不得实施。

### Q1-C：最小缓解

- 保留现有同步数据库留痕，只对非属主拒绝增加去重与对象级限流。
- 不存在分支仍不写业务审计；审计故障时 500 / 400 差异仍存在。
- 实施后 DB-134 只能标记“部分处置”，不能标记风险消失。

### Q1-D：显式接受残余风险

- 不改生产代码；在台账、交付说明和运维文档中明确接受四类残余风险。
- 可提出网关限流与审计表容量监控建议，但配置变更须另走批准流程。
- 这是风险接受，不是技术修复。

## 5. 范围边界

### 纳入候选范围

- `DatasetQueryService.detail`

### 明确不纳入

- 分级只能收紧等业务状态拒绝。
- 产品已成行后的上下架、变更、交互拒绝。
- 入驻资格、空间成员资格、治理例外。
- 成功操作留痕、历史数据回改、其他服务同型问题。
- 新消息中间件、新错误码、新依赖、门禁配置修改。

## 6. 异常与边界行为（方向级）

1. 限流必须发生在“已判定为拒绝”的统一分支、且早于审计写入；不能先按对象是否存在分流。这样既不妨碍属主正常访问，也让已知 / 未知对象的超限响应同形。
2. 去重键不得包含属主、空间、状态或“对象是否存在”等分支结果。
3. 历史留痕只读保留；新方案不得回改历史行。
4. 多实例下进程内去重 / 限流会放大额度，必须在高保真中明确单实例边界或选择跨实例方案。
5. 固定时间窗口边界可能产生相邻窗口各一条记录，须作为可接受边界或改为滑动窗口。
6. 任何方案都不得削弱认证、权限点、服务端属主判定和既有统一响应封套。

## 7. 规格缺口声明

- 当前规格明确要求拒绝留痕与防枚举，但未规定审计存储形态、同步 / 异步、去重窗口、限流阈值及猜测不存在对象的留痕方式。
- Q1-A / Q1-C 预计可在规格内通过设计确认落地；Q1-B 如采用有损或最终一致审计，须先提交规格 / ADR 变更申请。未批准前，该部分不在编码范围。
- 不允许在设计阶段私自把“必须留痕”改成“尽量留痕”。
