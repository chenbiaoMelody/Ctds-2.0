## 1. 做什么（业务可读）

### 1.1 问题（台账 DB-41 四族，均属"同一段代码抄了多份/两套写法并存"）

| 族 | 业务可读描述 | 现状证据（盘点实证） |
| --- | --- | --- |
| ① URL 编码分裂 | 中文/特殊字符参数进网址时，有的域做了转义保护、有的域裸拼——一旦出现含特殊字符的编号就会请求出错 | did 域 8 处全编码；subject 域 10 处仅 1 处编码（**登记增量发现**）；catalog/space/contract 三域 0 编码 |
| ② 查询串与拦截三副本 | "分页查询串拼装"与"空主体拦截（零请求直接提示）"两段逻辑在 contract/catalog/space 逐字抄了三份，did/subject 还各有一个变体 | `contract.ts:357` / `catalog.ts:219` / `space.ts:166` 三副本逐字同；`did.ts:126` 变体；`subject.ts:170` 内联 |
| ③ 角色头第 3 份 | "页面级角色头"函数 catalog 与 contract 函数体逐字相同（第 3 份同构），三域请求包装函数也随之三份同构 | `demoIdentity.ts:61/66` 逐字同构（space 同构不同值）；三域 `xxxJson` 包装除头函数外逐字同 |
| ④ 分页参数两套 | 列表查询函数的入参写法两套并存：contract/did 用"一个对象装全部参数"，catalog/space/subject 用"按位置逐个传" | 单对象 9 函数（contract 7 + did 2）；位置参数 17 函数（catalog 10 + space 6 + subject 1） |

### 1.2 收敛方向（对应用户可见影响 = 零）

1. **①统一编码**（方向 Q1）：字符串型编号进网址一律转义（建议口径 A）——对现行全部字母数字编号是无感变化（转义前后逐位相同），属"加装保险丝"；
2. **②沉淀公用层**（落点 Q3）："分页查询串拼装"与"空主体拦截"收敛到 `client.ts` 公用层唯一一份，三域改为一行调用——行为与现在逐字等价；
3. **③收敛角色头**：三个同名导出函数保留（调用面零变），函数体收敛为一份带参数的私有工厂；
4. **④统一分页签名**（方向 Q2）：建议统一为"单对象"（contract/did 新例推广）——纯函数签名形态变化，函数名与请求 URL 不变。

**用户可见影响 = 零**：界面渲染、交互流程、请求 URL、错误提示全部不变；本卡交付后"任一列表页翻页/筛选/操作行为如常"即验收演示口径。收益是结构性的：这四类横切逻辑今后只有一份实现，第三消费方（3.5 交付域等）出现时不再放大漂移。

## 2. 不做什么（范围边界）

1. **不改后端**、不改任何请求 URL 与错误码语义、不改库表；
2. **不改门禁配置**（红线 3）；不夹带 DB-43（门禁可观测性）/ DB-44（E6 双视图收敛）/ 跟踪-20 / 跟踪-22；
3. **did/subject 不新增空主体拦截**——补拦截 = 新增"零请求拒绝"行为，违反零行为变更锚（有意不收敛点，hifi §4 留痕）；
4. **不改 api 模块导出函数名**（仅签名形态统一与内部实现收敛）；
5. 不做"顺手优化"：凡四族之外的重复/风格问题（如常量文案落点、types 收口）发现即登记不实施；
6. 不引入新依赖、新框架抽象（工厂即普通函数，章程 4.1 平庸化）。
