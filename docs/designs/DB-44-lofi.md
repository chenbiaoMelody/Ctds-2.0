## 1. 做什么（业务可读）

### 1.1 问题：同一块"合约只读分区"被抄了两份，且已经开始不一致

合约治理页（运营档查看任意合约）的"治理详情"抽屉，与合约详情页（参与方查看自己合约）是**同一批展示块的两份拷贝**——总览、条款全文、策略五要素、条款版本链、合约留痕，两边的模板代码几乎逐字相同，函数（策略行渲染）逐字两份。台账 DB-44 记录的事实是：**复制已经开始漂移**——同一个"条款全文"块，详情页显示"标的（subject_matter）"这样的**业务名称**，治理页却直接把数据库键名 `subject_matter` 摊给用户看。

立卡批逐字比对（`main == origin/main == 6383a80`）另发现**第二处漂移**（台账原文未列，本卡立项）：

| 分区 | 详情页 | 治理抽屉 | 判定 |
| --- | --- | --- | --- |
| 总览（A） | 3 列 12 项（状态带颜色标签；含创建 / 更新时间） | 2 列 10 项（状态纯文本；生效 / 完结合并一行；无创建 / 更新时间） | 差异（治理视角简化，**建议保留**） |
| 当前条款全文（B） | 标签 = 槽位**名称**（键）（经模板框架映射） | 标签 = **键名直显** | **漂移 1（本卡收敛，台账已登记）** |
| 策略五要素（F） | `h4` + 2 列 6 项 | 同（模板逐字相同） | 同构（收敛为单点） |
| 策略行渲染函数 | 逐字一份（取值走 detail 根部） | 逐字一份（取值走治理包装层） | 同构（收敛为单点） |
| 条款版本链（C） | 含**「双方确认时间」列** | **无该列** | **漂移 2（本卡立项：建议对齐补齐）** |
| 合约留痕（H） | 6 列（列宽 120 / 180 系） | 6 列（列宽 110 / 170 系；分页状态变量各自命名） | 同构（列宽差异，功能等价） |
| 动作条 / 签署存证 / 策略与使用区 | 有（参与方） | 无（治理只读，设计如此） | 有意差异（**保留**） |
| 强制终止 | 无 | 有（治理动作） | 有意差异（**保留**） |

### 1.2 收敛方向（对应用户可见影响 = 极小且可控）

1. **抽一个共享组件**（建议 Q1-A）：把上述"只读五分区"（总览 / 条款全文 / 策略五要素 / 版本链 / 留痕）搬进一个共享组件，两个视图都引用它；策略行渲染函数与"槽位名"逻辑从此**只有一份实现**（单点）；
2. **对齐漂移 1**（台账口径）：治理侧改为与详情侧同一口径——优先取模板框架里的**业务名称**，取不到才回退键名；
3. **对齐漂移 2**（建议，属可见变更）：治理侧版本链补上「双方确认时间」列，与详情页一致；
4. **保留有意差异**：两视角各自的字段集（治理简化总览）、治理独有的强制终止、详情独有的动作条与策略使用区——这些是**产品设计**，不是脏拷贝，本卡不动。

**用户可见影响**：治理详情抽屉里"条款全文"的标签会由 `subject_matter` 变为 `标的（subject_matter）`（业务上更可读）；版本链多一列"双方确认时间"。其余所有列表、详情、按钮、错误提示**零变化**。

**收益（业务口径）**：同一块界面今后只有一份代码，改一处两边同时生效——不会再出现"改了一边、另一边还是老样子"的隐性不一致（本次漂移就是这么来的）。

4. **不新增业务功能**：不补治理侧动作条、不补详情侧强制终止；
5. **不改 `constants/contract.ts`**（中文仍一律取常量；新组件同样受源集守卫约束）；
6. 不引入新依赖、新框架抽象（共享组件 = 普通单文件组件，章程 4.1 平庸化）。

## 5. 主要流程（业务语言）

1. 参与方在合约详情页查看合约 → 五分区由共享组件渲染（外观与现在完全一致）；
2. 运营在合约治理页打开某合约的"治理详情"抽屉 → 同一共享组件以"治理视角"渲染（字段集按现状简化）；
3. 抽屉内"条款全文"标签优先显示业务名称（取得到模板框架时），取不到显示键名——与详情页表现一致；
4. 版本链、留痕区在两视角下结构一致（视 Q2-2 决定是否补齐"双方确认时间"列）；
5. 治理抽屉内的"强制终止"与详情页的"动作条 / 策略与使用"各留在自己页面，行为零变化。
