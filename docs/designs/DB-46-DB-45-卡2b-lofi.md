## 3. 待确认问题（Q1~Q5 + D1）

### Q1 范围：23 项全收，还是 18 项 + 新候选分卡
- **建议 A：23 项全收。** 理由：5 条新候选与 18 项同属"门禁可信性"面（清扫误伤 / 探针锚 / 环境口径），同卡清算可一次回归验证（selftest + 全仓门禁各一遍），分卡反而两次全链成本；体量增量 ≈ +70 行。
- 备选 B：仅 18 项，新候选另卡。影响：本卡更快闭合，但 5 项再挂一个周期（与"清零挂账"目标相悖）。

### Q2 config V1.12（C4/C5）是否随卡执行
- **建议 A：随卡执行。** 内容 = C4 `gateSelfTest.note` 第三数据点（「125 断言·58s」）与余量口径（"7 倍以上"→按 58s 实为 5.2 倍）；C5 `OSTYPE`/`OSType` 键名大小写统一。**零阈值、零阶段范围、零扫描面、零五态语义改动**（note/键名级）。变更流程四件套预设：`changeLog` V1.12 + ADR-018 修订记录（V1.10）+ README 留痕 + **ConfigSha256 新基线外部登记**（沿用"当前哈希不内嵌 changeLog"原则）。
- 备选 B：只登记不执行。影响：口径不一致继续存在（C4 的"7 倍以上"与实测 5.2 倍不符），下轮评审必再提。

### Q3 B2 内联进程调用收敛口径
- **建议 A：零行为变更重构。** 把 mvn/npm 段内联的 ProcessStartInfo 调用统一到既有辅助函数（`Invoke-MetricProcess` / mvn 段同款），以 **selftest 全量回归 + 全仓门禁 GREEN** 为证；任何行为差异 → 停报改登记（红线 4 精神）。
- 备选 B：仅登记。影响：代码重复留存（评审③视角会再次登记），但零风险。

### Q4 B7 action SHA 钉住
- **建议 A：实现（逐 action 核验）。** `actions/checkout` / `setup-java` / `setup-node` / `setup-python` / `upload-artifact` 等版本 tag → **官方仓库 commit SHA**（每个 SHA 须官方注册表/`gh api` 核验存在性后落盘；不可核验的 action 保持 tag 并登记原因）。供应链收益：防 tag 漂移/劫持。
- 备选 B：全部登记不做。影响：供应链评审②视角会持续登记。

### Q5 新候选 N1（清扫误伤面）处置
- **建议 A：复核后择一。** 优先评估"增强排除"（如按进程启动时间早于本阶段判定为并行构建而跳过）——若实现复杂度高或引入新脆性，则**登记接受**（附业务理由：双特征 + 祖先链 + 仅超时触发的残余面），不留无限期"待办"。
- 备选 B：仅登记。影响：同 A 的登记分支，但少一次复核。

### D1 体量
- 预估 ~400–450 行（脚本/测试/config/文档；业务代码零改动），略超 400 上限 → **建议不拆分**（沿卡 2a "含测试与注释"口径；实测若 >500 行再拆）。
