## 低保真内容（结构草图）

### 做什么（逐条对应产出定义）

1. 新建公共组件 `common/logging`（模块名=目录=artifactId=`common-logging`，与 errorcode/pagination 平级——T10 口径）；依赖 `common-errorcode`（错误码进日志上下文），复用其 `TraceIdFilter` 的 traceId；
2. 结构化日志：所有服务日志输出为"一行一条 JSON"（时间、级别、traceId、错误码、模块、消息、上下文字段），人能读、机器能检索；
3. 审计事件埋点：业务代码一行调用即可记录"谁、何时、对什么、做了什么、结果如何"；事件异步写出，不拖慢业务；
4. AI 调用日志预留：仅表结构占位（DDL 脚本 + 字段说明文档），不实现任何功能逻辑（PRD G4：V1.0 仅预留，V1.5 由 WBS 3.10.3 填充）；
5. example-service 端到端接入：现有接口演示"JSON 日志 + 错误码入上下文 + 审计事件落文件"。

### 不做什么（V1.0 边界，防蔓延）

- 不做分布式链路追踪（OpenTelemetry 等，后续任务）；
- 不做日志采集/传输服务端（Filebeat/Logstash 属部署侧配置，不属本组件）；
- 不做审计事件的数据库持久化（待 2.4.10 持久层组件就绪后接入，本任务先落文件）；
- 不实现 AI 调用日志的功能逻辑（仅表结构占位）；
- 不更换日志框架（沿用 Spring Boot 3.5 自带 logback，符合 ADR-001 技术栈冻结）。

### 结构组成（common/logging 内）

- `LogContext`：日志上下文封装（traceId / 错误码 / 业务标识，写入门面）；
- `JsonLogSetup`：JSON 格式自动装配（业务服务零配置生效）；
- `AuditEvent` + `AuditEventType`：审计事件模型（谁 / 何时 / 对什么 / 做什么 / 结果 / 明细）；
- `AuditRecorder`：审计埋点接口（业务代码唯一依赖点）+ 默认异步文件实现（按天滚动 JSONL 文件，应用 `logs/` 目录）；
- AI 调用日志表结构占位（DDL + 字段说明）；
- 新依赖：logstash-logback-encoder（见待确认问题 1）。

### 主要流程（3–5 步）

1. 业务代码调用 `AuditRecorder` 记审计事件，或抛 `BizException`（带错误码）；
2. 组件把 traceId / 错误码 / 业务标识写入日志上下文；
3. 日志统一以 JSON 一行输出（控制台 + 文件）；
4. 审计事件进入异步缓冲，后台线程写入按天滚动的 JSONL 文件（不阻塞业务线程）；
5. 演示：调用 `GET /api/v1/greetings`（含人为制造一次参数错误），控制台与文件中可见 JSON 日志和审计事件，错误码字段可检索。

### 待确认问题（需要你裁决）

1. 【依赖审批】JSON 结构化日志需新增第三方依赖 **logstash-logback-encoder**——业界最主流的 logback JSON 编码器，Apache 2.0 许可，已在 Maven Central 核验真实存在（net.logstash.logback:logstash-logback-encoder）。**建议：批准引入**，版本取 8.x 系列（兼容 Spring Boot 3.5 管理的 Jackson 2），精确版本在高保真设计锁定并更新依赖登记。备选：不引入依赖、维持纯文本日志（零依赖，但日志不可机检、后续采集与审计对账困难，不推荐）。
2. 【审计事件 V1.0 落地形态】先落"按天滚动的 JSONL 文件"（应用 `logs/` 目录，按服务区分），数据库持久化待 2.4.10 持久层就绪后接入。**建议：同意**（先能记、再入库，避免本任务膨胀）。
