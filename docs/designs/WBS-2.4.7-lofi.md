## 低保真内容（结构草图）

### 场景判定（决定依赖选型，结论先行）

幂等与分布式锁有一个共同前提：**需要在多个服务实例之间共享"谁正在处理/谁持有锁"的状态**——单机内存做不到跨实例一致（本平台是微服务架构，章程 §3）。按 ADR-001 已冻结的技术栈，Redis 正是为此准备的中间件。→ **幂等与锁均基于 Redis 实现**（业界 Java 主流做法），另配"内存实现"作无 Redis 环境的兜底（详见"做什么-6"）。

**锁实现判定**：分布式锁用 **Redisson**（Java 分布式锁事实标准库，RLock 提供自动续期看门狗/可重入/等待超时）。理由（业务语言）：
1. 锁协议的正确性（持锁方崩溃后锁自动释放、同一线程可重入、释放时校验持有者）由成熟库保证——与 2.4.6 国密"组件只封装、禁止自研算法"同一条逻辑：**锁协议也不自研**，杜绝"锁超时死锁/误删他人锁"这类经典生产事故；
2. 全网 Java 教程与 AI 语料最主流，外部顾问最容易接手；
3. 依赖核验：官方注册表 repo1.maven.org 实测，`redisson-spring-boot-starter` 3.x 最新 = **3.52.0**（4.x 面向 Spring Boot 4.1 与本项目 3.5 不符，不采用）；其 pom 声明 spring-boot 3.5.5，与项目 Spring Boot 3.5.16 同主次版本兼容；该 starter 内部自带 `spring-boot-starter-data-redis`（排除 jedis/lettuce，用自研连接），故**一个依赖同时满足幂等（RedisTemplate）+ 锁（RLock）两个组件**。

依赖核验与登记：PO 预授权按上述原则自主选定（沿 2.4.5/2.4.6 先例）；本设计确认后，编码会话履行 ① 登记 `docs/dependencies.md`（审批栏注明 PO 预授权 + 本 lofi 确认记录）→ ② 根 pom `dependencyManagement` 锁版 `3.52.0` → ③ 引入时以 optional 声明（沿 2.4.5 oauth2-resource-server 先例，避免默认波及未开启服务）。

### 做什么（逐条对应产出定义）

1. 新建公共组件 `common/idempotency`（模块名=目录=artifactId=`common-idempotency`，与 errorcode/pagination/logging/auth/crypto 平级，一个工作包一个模块）；依赖 `common-errorcode`（拒绝场景用统一错误码）、`common-logging`（幂等命中/锁失败联动审计事件，可开关）；
2. **幂等组件**：`@Idempotent` 注解 + 切面。业务代码一行标注"这个方法以什么为幂等键"，组件保证同一幂等键只执行一次业务、重复请求取回首次结果（模式 B，见待确认问题 3）。幂等键 = 方法参数表达式（如订单号）+ 全局前缀，可配结果缓存有效期（TTL），过期后允许重新执行；
3. **分布式锁组件**：`@Locked` 注解 + 切面。业务代码一行标注"这个方法的互斥键"，组件保证同一互斥键的并发调用只有一个能进入，其余等待或超时返回（Redisson RLock：看门狗自动续期防死锁、可重入、释放校验持有者）；
4. **接口抽象 + 双实现**：幂等存储接口 `IdempotencyStore`、锁服务接口 `LockService`（沿 auth 的"业务零改动可替换"边界）：**Redis 实现**（默认，production 语义）+ **内存实现**（无 Redis 环境兜底：单测、演示、单机部署）；配置项切换 `ctds.idempotency.mode=redis|memory`（默认 redis；配了 Redis 连接即用，无 Redis 时显式切 memory 可运行）；
5. **统一错误码**：新模块段 `1002`（沿 ADR-006"1001+ 顺延规划"），幂等冲突/锁不可用等场景给统一码与对外文案（errorcode 组件既有码与行为零改动，沿用 BizException + 全局映射）；
6. **自动装配与配置项**：组件开关 `enabled`（沿 2.4.5/2.4.6 惯例，false 不注册切面）、Redis 连接配置、键前缀、默认 TTL、审计联动开关；
7. **example-service 端到端演示**（沿 2.4.6 SecretNote 惯例，内存仓储 + 集成测试 + HTTP 实测）：
   - "提交订单"端点：同一订单号重复提交 → 只处理一次、第二次返回首次处理结果（幂等演示）；
   - "扣减库存"端点：并发扣减同一商品库存 → 锁保护不超卖（锁演示）。

### 不做什么（V1.0 边界，防蔓延）

- **不做分布式事务**：幂等只防"重复执行"，不负责多表/多服务操作的原子性（分布式事务属后续业务包，另行设计）；
- **不做消息投递语义**：Kafka/RocketMQ 的"精确一次投递"是消息中间件自身能力，本组件解决的是"业务处理幂等"（消息消费场景组合使用时：消息幂等键 → 本组件去重）；
- **不做数据库实现**：MySQL 唯一键/悲观锁可做幂等与锁，但 Redis 已在栈内且性能与语义更优，避免同一能力双中间件依赖；
- **不做锁的高级形态**：公平锁/读写锁/红锁不在 V1.0 注解层暴露（Redisson 客户端本身具备这些能力，业务确有需要时直接注入客户端使用，本组件不重复包装）；
- **不做幂等键注册表/管理界面**：键的冲突查询、清理界面属运维工具，不属公共组件职责；
- **不引入嵌入式 Redis 测试依赖**：Redis 实现测试策略见"规格缺口声明-2"（沿 2.4.11 Testcontainers 未建的现状）。

### 结构组成（common/idempotency 内）

- 幂等：`@Idempotent` 注解、`IdempotencyAdvice`（切面）、`IdempotencyStore` 接口、`RedisIdempotencyStore`（SETNX + 结果缓存 + TTL）、`InMemoryIdempotencyStore`（ConcurrentHashMap + TTL 清理）；
- 锁：`@Locked` 注解、`LockAdvice`（切面）、`LockService` 接口、`RedissonLockService`（RLock tryLock/释放）、`InMemoryLockService`（互斥 + 超时，进程内）；
- 装配：`IdempotencyAutoConfiguration` + `LockAutoConfiguration`（`@ConditionalOnProperty` 开关、`@ConditionalOnMissingBean` 可替换）、`IdempotencyProperties`（配置项）；
- 依赖：`redisson-spring-boot-starter:3.52.0`（optional）、`common-errorcode`、`common-logging`。

### 主要流程（3–5 步）

**幂等流程（模式 B）**：
1. 请求到达带 `@Idempotent` 的方法，切面按 SpEL 算出幂等键（如订单号）；
2. 尝试在 Redis 写入"执行中"标记（SETNX，带 TTL）——写成功 = 首次请求，放行业务；
3. 业务执行完成，把结果写入幂等键对应缓存（TTL）；
4. 重复请求（同幂等键）SETNX 失败 → 读缓存：有结果 → 直接返回首次结果（业务不重复执行）；仍在执行中无结果 → 按配置返回"处理中"统一错误（或等待，见 hifi）；
5. 幂等键到期自动清理，允许重新执行（业务侧按需设计键粒度与 TTL）。

**锁流程**：
1. 请求到达带 `@Locked` 的方法，切面按 SpEL 算出互斥键（如商品 ID）；
2. 尝试获取 RLock（可配等待超时与自动释放时间，看门狗持锁期间自动续期）；
3. 获取成功 → 放行业务 → finally 释放；获取超时 → 返回统一错误码"操作繁忙，请稍后重试"（不暴露内部实现）；
4. 并发演示：两个请求同时扣同一商品库存，锁保证只有一个进入扣减，库存不为负。

### 待确认问题（需要你裁决）

1. 【基础设施判定】幂等与锁都需要"跨实例共享状态"，ADR-001 已冻结 Redis → **基于 Redis 实现**；另配**内存实现**兜底（无 Redis 的演示/单测/单机环境可用，配置一行切换）。**是否认可"Redis 为主 + 内存兜底"这套架构**？（备选：纯 Redis 不提供内存兜底——演示环境必须起 Redis，单测依赖中间件）
2. 【锁实现判定】分布式锁用 **Redisson**（业界标准库：看门狗自动续期防死锁、可重入、超时释放都由成熟库保证，与"不自研算法"同逻辑**不自研锁协议**）；已核验官方注册表 3.52.0 与 Spring Boot 3.5 兼容。**是否认可**？（备选：只用官方 spring-data-redis 自封装锁脚本——依赖更少，但锁协议自研、死锁/误删风险自担）
3. 【幂等语义】幂等组件提供哪种业务保证：**模式 B 结果复用（推荐）**——重复请求不重复执行、返回首次执行结果（数据流通平台"重复投递不重复处理 + 可取回首次结果"是刚需）；还是模式 A 防重复提交——重复请求直接拒绝不返回结果。**选哪个**？（选 B 则 A 可作其简化子集一并支持）
4. 【使用方式与演示】业务代码一行注解：`@Idempotent(key="订单号")`、`@Locked(key="商品ID")`（key 支持方法参数表达式）；example-service 加两个演示端点"提交订单（幂等）""扣减库存（锁）"。**是否认可**？
5. 【错误码】新模块段 `1002`（沿用 9 位格式与全局映射，errorcode 组件零改动），为"重复提交/处理中/锁繁忙/锁服务不可用"等场景定统一错误码与对外文案（不暴露内部实现）。**是否认可**？
