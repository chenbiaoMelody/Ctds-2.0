## 1. 方向概述（业务语言）

给两个"能跑起来"的软件各自写一份"集装箱装箱说明书"（Dockerfile）：后端服务装进标准 Java 运行箱、前端页面装进标准网页服务器箱——以后不管放在谁的机器上，行为都一样。再写一套 Kubernetes 编排模板（"机房摆放图纸"）：声明每个箱子开几个副本、怎么互相找到对方、崩了怎么自动拉起。本任务交付**模板本身**及其单箱实测；"一条命令把整套箱子搬进机房"属于下一任务 2.5.2 一键部署工具链。

## 2. 范围判定（逐项）

| # | 判定项 | 结论 | 理由 |
| --- | --- | --- | --- |
| 1 | **容器化对象** | 可运行制品共 2 个：example-service（Boot fat jar，8080，默认 profile 无库自足）+ frontend（静态产物）；common/* 为库不容器化；connector-sdk 沿 ADR-012 占位留痕 | "各模块容器化"按可运行口径覆盖；6 个 common 组件是 jar 库由服务携带，单独成箱无业务意义 |
| 2 | **构建产物外部供给**（Dockerfile=打包说明书，非多阶段自构建） | Dockerfile 只做"运行环境 + 拷入已构建产物"：后端 COPY target jar（由 2.2.6 流水线 N3 或本地 mvn package 供给），前端 COPY dist（N4 供给） | 容器内构建需重新下载全部 Maven/npm 依赖：本机 aliyun maven 镜像与 npmmirror 配置均不可进容器，自构建慢且网络不稳；与 2.2.6"流水线产构件、下游消费"契约同构。多阶段自构建留观察项，CI 环境再评估 |
| 3 | **基础镜像选型** | 后端 `eclipse-temurin:17-jre`（官方 OpenJDK 发行，ADR-001 Java17 冻结栈配套）；前端 `nginx:1.29-alpine`（官方稳定线 + alpine 最小面）；**tag 显式锁定禁 latest**（沿 ADR-010 精神） | 登记口径：dependencies.md 新增"容器基础镜像"节（镜像:tag/用途/核验来源），随 ADR-013 双留痕。拉取通道：直拉 Docker Hub，失败则 `docker.m.daocloud.io` 镜像源拉取后 retag（本机已有该源使用痕迹），实测留痕 |
| 4 | **K8s 模板范围** | `deploy/k8s/`：两个模块各 Deployment + Service（ClusterIP），共 4 份 YAML；镜像字段用占位符 `IMAGE_PLACEHOLDER`（注入机制属 2.5.2）；探针用 tcpSocket（greeting 端点有鉴权 401，HTTP 探针会假红）；资源 requests/limits 基础值 | 单任务卡最小可行；MySQL/Redis 等中间件编排、Ingress、副本策略调优属 2.5.2+；注入脚本不在本任务做（防膨胀） |
| 5 | **规范载体** | 新建 ADR-013《容器化部署模板规范》（容器化对象口径、基础镜像表、Dockerfile 约定、K8s 模板约定、端口/探针约定）+ dependencies.md 基础镜像节 | 2.5.2 一键工具链、2.5.3 监控都要消费同一套约定，沿 ADR-009~012 惯例固化 |
| 6 | **验证方式** | ① 后端：mvn package → docker build → docker run 冒烟（容器起、端口通、curl 端点响应）；② 前端：npm run build → docker build → docker run 冒烟（首页 200）；③ K8s 模板：kubectl 客户端侧离线校验（本机 kubectl 1.36.1 已装）；**不做集群部署演练**（2.5.2"开发/测试环境演练通过"的口径） | 单箱实测保证"模板可跑"，集群演练归 2.5.2，职责不越界 |
