## 3. 主要流程（业务语言）

1. **来访验证（对端来本空间办事）**：对端方提交"对端空间标识 + 对端 DID + 原文 + 签名"→ 系统经互认通道取对端样例（公钥 / 对端状态 / 对端绑定）→ **三查**：① 签名核验（SM2 验签）② 对端状态核验（有效/已吊销）③ 对端绑定核验（模拟对端返回的绑定状态）→ 三查全过 = "验证通过"，任一不过 = "验证不通过 + 明确原因"→ 留痕（四要素 + 失败原因）。
2. **出向验证（本空间主体去对端办事）**：本空间发起"验证本空间某 DID"→ 模拟对端读取本空间该 DID 当前状态 → 回放结论（有效→通过 / 已吊销→不通过）→ 留痕（方向 = 出向）。
3. **样例清单（演示取用）**：返回三条预置样例（有效 / 对端已吊销 / 签名被篡改），执行人按清单选择即可，无需手输（剧本附录 A "取用口径"）。
4. **能力未开放时**：真实实现交付前，占位实现返回"该标准互联功能尚未开放"（1003C0001），不返回任何伪结果（行为 5 验收标准 4）。

### 待确认问题（需要人裁决的业务选项，含建议倾向）

**Q1｜互认能力落位（协议实现与 HTTP 端点分别放哪里？）**
- **A（建议）协议实现落 `std-adapter` 的 `did` 域（替换占位），HTTP 端点落 `services/did`**：ADR-008 收口纪律要求一切"与外部标准打交道"的代码只允许落在 std-adapter，而 std-adapter 是无端口的纯 jar 库 → 协议逻辑必须在 std-adapter，对外承载必须借业务服务；DID 能力的归属服务是 `services/did`（3.1.11 管理界面也将调用它），互认留痕也落 DID 库，单一事实源。
- B 端点落 example-service：把业务能力放进演示壳服务，3.1.11 界面与后续业务要反向依赖演示服务，边界倒置。
- C std-adapter 起独立服务：ADR-008 §2 已弃（凭空多部署/运维面）。

**Q2｜"协议方法签名"如何冻结？（本包核心决策）**
- **A（建议）只冻结"业务口径方法"，并诚实登记**：把三类方法（来访验证 / 出向验证 / 样例清单）作为**平台内部业务口径**冻结，字段用业务语言（空间标识、DID、原文、签名、状态、绑定），并在 ADR-008 补记中明示"这不是信通院协议签名；规范文本取得后按变更流程冻结协议签名并替换/扩展本域方法"（ADR-008 特别说明已预留该路径）。
- B 按公开资料拟定协议报文签名：规范文本未入库即猜需求，ADR-008 §2 已明确弃。
- C 本包不实现（只保留"未开放"）：规格行为 5 要求真实互认能力，C 等于不交付（占位答复已由骨架期承载）。

**Q3｜模拟对端三态样例如何承载并保证"签名真实"？**
- **A（建议）样例以资源文件入库（JSON），签名为制作期真实 SM2 签名**：制作期一次性生成对端密钥对 → 公钥入样例、**私钥不入库**（只留在 gitignored 生成目录并即刻废弃）→ 原文 + 真实签名入库；运行期仅带公钥验签，不内置私钥。三态 = 有效（验签过 + 对端状态有效）/ 对端已吊销（验签过 + 对端状态已吊销）/ 签名被篡改（签名与原文不匹配）。
- B 运行时用测试私钥现签：违背"运行环境不内置对端私钥"，且"篡改态"无从构造（剧本要求签名与原文不匹配）。
- C 格式仿真签名：剧本附录 A 明确禁止（会产生伪结果，违背 ADR-008 防假象口径）。

**Q4｜来访验证的"三查"在互认场景如何落地？**
- **A（建议）三查全部按对端口径，经互认通道取数（不查本空间主体库）**：① 签名核验（样例公钥 SM2 验签）② 对端状态核验（样例提供的对端状态）③ 对端绑定核验（样例提供的对端绑定状态）；失败原因枚举沿用 3.1.9 五值（`SIGNATURE_INVALID` / `REVOKED` / `SUBJECT_BINDING_FAILED`（对端绑定失效）/ `NOT_REGISTERED`（对端样例不存在）/ `BINDING_UNAVAILABLE`（互认通道不可用））。
- B 把对端 DID 拿回本空间注册表解析：语义错误（对端主体不在本空间主体库，规格行为 5 规则 2 已明示）。
- C 只做签名 + 状态两查："三查"少一查，与规格不符。

**Q5｜互认留痕如何承载？**
- **A（建议）did 服务新增独立表 `did_interop_log`（V3 迁移）**：字段 = 方向（来访/出向）/ 对端空间标识 / DID / 结果 / 原因 / 时间；口径同行为 3（不存原文；输入类拒绝与内部错误不留痕）。互认是独立业务行为，独立表语义清晰。
- B 复用 3.1.9 的 `did_verification_log`（加方向与空间标识列）：改动 3.1.9 已交付契约与表语义（本空间验证与互认验证混表），且历史数据语义需回填，得不偿失。

**Q6｜互认端点的访问控制？**
- **A（建议）演示期无鉴权 + 诚实边界登记（ADR-017 补记）**：互认验证的调用方是"对端系统"，演示期凭令牌不现实；真实边界 = 回环网络隔离（沿 3.1.9 解析/验证端点先例），上线前由网关 + 真实令牌收紧。
- B 要求 `did.admin` 角色：与"对外验证能力"定位不符（对端不会持有本空间角色）。

**Q7｜出向验证（双向口径）如何实现？**
- **A（建议）端口倒置：模拟对端经 `LocalDidStatusPort` 读取本空间 DID 状态**：std-adapter 定义端口，did 服务提供实现（进程内委托既有解析能力），装配时注入模拟对端 → 出向验证无 HTTP 自调用、不新建权威源。
- B 模拟对端经 HTTP 回调本空间解析端点：绕一圈自调用，多出端口/超时/地址配置，收益为零。
- C 只做来访验证不做出向：规格行为 5 规则 1 明确双向，剧本 S4 步骤 4/5 承载，不可省。

## 5. 已知风险与实施前置检查项

**风险**：
1. **协议未冻结的诚实风险**：本包交付的是"业务口径互认 + 模拟对端"，须在交付说明与 ADR 补记中明示"非信通院协议实现"，避免被误读为已具备标准互认资质；
2. **样例真实性依赖制作期**：一旦误用格式仿真签名，互认将返回伪结果（剧本已明令禁止）→ 制作步骤写入 hifi 前置检查项并留痕；
3. **"回放"语义**：出向验证的结论由模拟对端回放（非真实对端行为），交付说明须标注演示态；
4. **留痕表增长**：演示期量小，语义与 3.1.9 一致（不存原文）。

**实施前置检查项（编码会话第一步，逐项实测留痕）**：
1. 演示环境三服务（8080/8081/8082 回环）与 Docker 容器状态核验；
2. `common-crypto` 的 `Sm2Service.verify(data, signature, publicKeyHex)` 可用性与签名/公钥编码口径实测（130 hex 非压缩公钥）；
3. 样例生成一次性程序运行留痕（生成脚本不入库，产物 JSON 入库）；
4. `example-service` 探活端点当前输出基线（替换前为 `did` 域 `implemented=false`）。
