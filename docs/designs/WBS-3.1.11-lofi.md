## 3. 主要流程（业务语言）

1. **看记录**：运营管理员打开「DID 管理」→ 默认列出全部签发记录（分页）→ 可按主体申请编号或状态筛选 → 每行显示主体申请编号、签发序号、DID、状态（有效 / 已吊销 / 待签发）、密钥引用、签发时间。**未入驻的主体查不到记录**（未入驻不签发）。
2. **吊销**：在某条"有效"记录上点"吊销"→ 弹窗填写理由（留空即被拦下，提示"吊销理由必填"）→ 提交后弹出二次确认，明确写着"**吊销不可逆**"→ 选"取消"：什么都没发生（状态不变、无留痕）→ 选"确认"：状态立即变"已吊销"，详情里的"操作留痕"出现一条含五要素的记录。
3. **重签**：对已吊销记录点"重签"→ 系统生成**全新的密钥对与新的 DID**（序号 +1）→ 列表出现新记录，旧记录仍在列表里（旧标识永不复用，可追溯）。
4. **重试**：对"待签发"记录点"重试"→ 签发补齐（含留痕）；若没有待签发对象，如实提示。
5. **演示与验证**：在演示区输入一段文本，选一个 DID → 点"生成演示签名"（**仅演示/调试期可用；关闭时明确提示"演示签名入口未启用"**）→ 得到签名值（可复制，供后续复核）→ 点"验证"看到"通过"或"不通过 + 明确原因（签名核验失败 / 状态已吊销 …）"→ 验证留痕列表出现一行（时间 / DID / 结果 / 原因，无原文）。
6. **解析**：输入 DID → 看到状态与公开要素（公钥等）；输入一条未登记的 DID → 以"业务答复"样式提示"未登记该 DID"（不是系统报错）。

### 待确认问题（需要人裁决的业务选项，含建议倾向）

**Q1｜界面范围：本卡是否包含"演示与验证"区（代签 / 验证 / 解析 / 验证留痕）？**
- **A（建议）包含，一次交付**：剧本 S1 步骤 1/3（"打开 DID 管理页（3.1.11 交付）"）、S2 步骤 1~6、S3 步骤 1~6 都把界面入口指向 3.1.11；其中"平台侧演示签名入口"已被规格 §6.6 列为 **3.1.11 设计强制项**；若不包含，则 S2 六步、S3 步骤 1/5 无法界面走查——"可演示"（交付定义）不成立，只能等新卡，验收链断裂。
- B 只做 WBS 行字面的"签发记录/状态/吊销管理页"：演示签名/验证/解析/留痕界面另立新卡（需编排师批新 WBS 行）。业务影响：3.1.11 可先验收，但 S2/S3 走查推迟到新卡；S3 步骤 1/5 跨卡执行（同一幕剧本跨两个交付物）。
- C 把演示面并入 3.1.12（测试补全与集成）：与 3.1.12 定位不符（该包是测试与联调，不是界面），会把"演示入口"变成测试包的隐性交付物。

**Q2｜记录列表的数据来源与端点形态？**
- **A（建议）新增只读端点 `GET /api/v1/did/records`**（`did.admin`；分页复用 `common/pagination` 的 `PageQuery/PageResult`，ADR-005 §3.2；支持 `subjectNo` 精确过滤、`status` 过滤）：记录视角的权威数据源是 `did_identity`（主体 / 序号 / DID / 状态 / 密钥引用 / 时间齐备），单查端点无法支撑列表与筛选。
- B 复用解析端点逐条查（`GET /api/v1/did/{did}`）：无法枚举（不知道有哪些 DID），且解析面按"公开要素"设计，不带主体与密钥引用。
- C 直接读库表（前端直连库）：不存在（前端只经 HTTP），且违背分层。

**Q3｜"记录状态"在界面怎么显示？会不会与"DID 状态两值"冲突？**
- **A（建议）列表显示既有三值，但把"待签发"标注为记录中间态**：`ACTIVE`=有效、`REVOKED`=已吊销、`PENDING_ISSUE`=**待签发（记录中间态，非 DID 状态）**——直接复用后端既有 `DidStatus`，**不新增状态枚举**；解析端点口径仍锁"有效 / 已吊销"两值（行为 2 规则 1）。理由：行为 1 规则 5 要求失败的记录停留"待签发"且可重试，管理页必须能看见它，否则"可重试"落不到界面。
- B 界面对外只显示两值、隐藏待签发记录：失败记录在界面上"消失"，运营无法重试（服务能力有、界面无处用）。
- C 新增"待签发"之外的展示态（如"签发失败"）：**新增枚举**，违反 ADR-017 §3。

**Q4｜吊销的界面交互形态？**
- **A（建议）"弹窗填理由 → 二次确认（明示不可逆）"两段式**：弹窗内理由必填（留空立即提示，不发起请求）→ 通过后弹出二次确认，确认文案含"吊销不可逆"与 DID 标识 → 取消 = 不发起请求（状态不变、无留痕）→ 确认 = 调既有吊销端点；后端 1005C0002（理由必填）/ 1005C0003（非有效不可吊销）作为兜底，界面**如实展示后端文案**（不吞、不改写）。沿 3.1.5 审核"二次确认"范式（`ElMessageBox.confirm`）。
- B 一步式（填理由即提交）：无法满足剧本 S3 步骤 3"先取消、再确认"的防误操作验收（且规格行为 4 规则 2 明示二次确认强制）。
- C 二次确认放在前端不发请求之外另加"输入 DID 复核"：超出规格要求的防误操作强度，增加执行负担（非必需）。

**Q5｜"重签"和"重试"是否都放到界面？**
- **A（建议）两个都做**：重签是**规格行为 4 规则 4 明确点名"由运营管理员在 DID 管理页发起"**，必做；重试源于行为 1 规则 5"停留待签发，可由运营重试"——管理页是唯一运营面，不做则该规则无界面落点。两者都**复用既有端点**，成功后刷新列表。
- B 只做重签：行为 1 规则 5 的"可重试"无界面落点（能力闲置），但不算违约（规则未点名界面）。
- C 都做成独立页面：多出两个页面与路由，操作分散（列表行内操作更贴合"看见即操作"）。

**Q6｜演示签名入口在"生产环境禁用"上如何落地？**
- **A（建议）配置开关 + 默认关闭 + 装配常驻**：`ctds.did.demo-signature.enabled`（默认 `false`，演示/调试期显式置 true 并走环境变量）；关闭时端点返回既有 `1000C0003`（资源不存在）+ 明确文案"演示签名入口未启用（仅演示/调试期）"。优点：① 是**代码门槛**（不是注释），默认态即生产禁用；② **不新增错误码**（满足 ADR-017 §3）；③ 前端能拿到明确文案直接展示。
- B 装配级不注册（`@ConditionalOnProperty` → 404）：关闭态前端拿到的是无业务码的 404，需在 API 层特判，且"未启用"与"路径写错"在排障时不可区分。
- C 常驻且不做开关（只靠文档声明"生产禁用"）：违反规格 §6.6"生产环境禁用该入口"的强制项（不能靠自觉）。

**Q7｜前端如何获得 `did.admin` 权限（演示期角色头）？**
- **A（建议）DID 页 API 模块内做页面级角色头覆盖**（`X-Ctds-Roles: applicant,reviewer,admin`）：`did` 服务把角色 `admin` 映射为权限 `did.admin`（`application.yml` 既有配置，零改动）。仅 DID 页的请求带该角色 → 影响面被限制在 did 服务；`subject`/`kms` 服务不识别 `admin` 角色（无配置），有效权限面不变。
- B 改全局 `demoRolesHeader()`（admin → `applicant,reviewer,admin`）：会让**example-service** 的 `admin` 角色配置（`greeting.read,greeting.delete,demo.read`）在演示期被意外激活（**最小权限面扩大**），超出本卡需要。
- C 在后端为 `reviewer` 角色追加 `did.admin`：把"审核员"与"运营管理员"两种职责混为一谈（职责分离被破坏）。

**Q8｜列表里的"关联主体"显示到什么程度？**
- **A（建议）只显示主体申请编号（`subjectNo`）+ 签发序号**：DID 域自有数据即可满足"关联主体"留痕要求（行为 1 规则 4）；主体名称/证照属 C-1.1 数据，did 服务只有 `{subjectNo, status}` 的最小暴露只读端点（3.1.9 口径），不为界面扩大暴露面。
- B 跨服务取主体名称一并展示：需扩展服务间只读契约（暴露面扩大）且引入跨服务拼接，收益仅是"看起来更友好"。
- C 界面上按编号让执行人手输主体：剧本 S1/S3 需要"查找某主体"，仅按编号筛选在演示时可接受（编号可从 C-1.1 流程获得）；如需友好检索，属后续体验优化（登记为建议，不在本卡）。

## 5. 体量预估与拆分对比（需编排师裁决）

**预估**：后端 ≈ 700~850 行（4 端点 + 仓储分页查询 + 4 视图 DTO + 测试）；前端 ≈ 800~1050 行（2 视图 + API/常量模块 + 路由 + 测试）；文档另计。合计 **约 1500~1900 行有效变更**，超章程 400 行指引。

| 选项 | 业务影响 | 交付节奏 | 风险 |
| --- | --- | --- | --- |
| **A. 不拆分（本卡一次交付管理面 + 演示面）** | 剧本 S1/S2/S3 可在界面完整走查；运营与演示入口一次到位 | 一个编码会话 + 一轮评审/走查 | 单次变更体量大（评审与走查窗口更长）；与 3.1.10 体量先例同量级 |
| **B. 拆分：本卡只做管理面（记录/状态/吊销/重签/重试）+ 新卡做演示面** | S1/S3 可先走查；S2 六步与 S3 步骤 1/5 的界面走查推迟到新卡（同一幕剧本跨两个交付物） | 两轮编码/评审/走查 | 需新立 WBS 行（变更流程）；两卡共用同一 API 模块与页面，存在返工改同一文件的窗口 |
| **C. 拆分：管理面 + 演示面分别由"界面卡"与"3.1.12"承载** | 3.1.12 定位被改写（测试包夹带界面） | 两轮 | 与 WBS 行 244 定位冲突，**不建议** |

> 说明：3.1.10 的"单卡单目标不拆分"先例（体量约 1443 行）不能直接套用——该包各交付项互为前提（拆分即产生不可运行的中间态）；本包管理面与演示面**技术上可独立交付**，故按章程④"超出自动拆分"原则如实提出，由编排师选择。

**已知风险**：
1. **演示签名入口的安全面**：入口一旦开启，即为"任意已登记 DID 的代签能力"（沿 ADR-017 §2.7 已登记的演示期残余口径）→ 默认关闭 + ADR 补记诚实边界 + 演示机可信；
2. **界面与剧本名称漂移**：剧本多处以"以实际交付为准"表述 → 交付后必须做一次界面核对修订（本卡交付物之一），否则执行人找不到入口；
3. **分页与过滤的注入面**：排序/过滤参数必须走参数化 SQL 与列名白名单（`PageQuery` 只做格式闸门，持久层仍须白名单映射——组件注释已明示）；
4. **演示角色造成的"看得见 vs 做得了"不一致**：普通演示角色可见入口被守卫拦下（回工作台），须以明确提示呈现，避免被误判为缺陷。
