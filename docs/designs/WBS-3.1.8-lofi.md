## 1. 做什么 / 不做什么（逐条来自规格，禁止规格外项）

### 1.1 做什么（W1~W7）

| 编号 | 做什么（业务可读） | 规格出处 |
| --- | --- | --- |
| W1 | **入驻即发身份**：主体经人工审核通过、状态变"已入驻"后，系统自动为该主体签发数字身份（DID）——申请人不需要提交任何申请；处于待认证/待审核/已驳回/认证失败的主体不产生 DID；企业/机构/政府部门口径一致（政务 CA 通道入驻同规则） | 行为 1 规则 1、7；剧本 S1 步骤 2（自动签发）、步骤 6（已驳回组不签发，负向） |
| W2 | **一主体同期只有一个有效身份**；同一主体的签发触发重复到达（重复提交、重放、运营重试）时，不产生第二份有效记录 | 行为 1 规则 2、6；剧本 S1 步骤 5 |
| W3 | **密钥国密化 + 私钥只进保险柜**：DID 密钥对为国密 SM2；私钥一律由 KMS（密钥管理服务）托管并**只在 KMS 内部参与签名运算**——任何数据库表、接口响应、日志中都不出现明文私钥，相关记录只出现"密钥引用"编号 | 行为 1 规则 3；分级规范 L4 |
| W4 | **留痕四要素**：每次签发留下 签发时间 / 关联主体（主体标识或申请编号）/ DID 标识 / 密钥引用 | 行为 1 规则 4 |
| W5 | **失败不改入驻结论、可重试**：密钥服务不可用等原因导致签发失败时，主体状态仍为"已入驻"，DID 记录停在"待签发"，运营管理员可重试；重试成功后补齐留痕 | 行为 1 规则 5；剧本非承载登记（由本包集成测试承载） |
| W6 | **身份注册表与身份说明书**：为每份 DID 生成公开的"DID 文档"（身份说明书：DID 标识、公钥、状态、关联主体、解析入口），与状态（有效 / 已吊销）一起落在平台数据库（§7 Q2 已裁决"平台库表承载"）——该库表是下游"解析与验证"（3.1.9）的唯一数据源 | 行为 2 规则 1 的数据面；§7 Q2=A |
| W7 | **吊销与重签的状态变更（写操作）**：吊销必须填理由、提交需二次确认（确认界面明示"不可逆"，交互归 3.1.11）、确认后立即生效、留痕五要素（操作人/时间/理由/DID/状态变更）；**不可逆**，继续使用需**重签**且**必须换全新密钥对**、旧 DID 标识永不复用。（归属见 §3 Q4） | 行为 4 规则 1~4；§7 Q4=A |
| W8 | **实施前置补齐**：给 KMS 的演示配置补"只许本机访问"绑定并重建构件；顺带实测 KMS 在"无数据库"默认配置下能否启动（既有疑点，见 §5 风险 1） | 规格 §5 依赖行；ADR-016 §2.7；DB-03 注记 |
| W9 | **演示可用性**：提供"重复触发签发联动"的注入方式（剧本 S1 步骤 5 要求随本包交付说明提供），让演示可重复执行 | 剧本行 115 |

## 2. 结构组成（模块/组件）

| 编号 | 组成 | 说明 |
| --- | --- | --- |
| S1 | **新建 DID 服务**（建议，见 §3 Q1） | 四层结构（接口层 / 应用服务 / 领域层 / 基础设施）+ 分层守卫测试 + 独立数据库 `ctds_did` + 迁移脚本 V1 + 演示配置绑定本机地址 + 无数据库默认配置可启动（全部沿用主体服务与 KMS 的既有工程范式） |
| S2 | **KMS 扩展**：SM2 密钥对托管 + 签名能力 | 私钥**不出 KMS**：调用方只提交"待签数据 + 密钥引用"，签名在 KMS 内部完成；同时补齐 KMS 的本机绑定（W8） |
| S3 | **主体服务衔接**：入驻后触发签发 | 在审核通过**提交成功之后**把"某主体已入驻"告知 DID 服务（形态见 §3 Q3）；幂等键 = 主体编号 |
| S4 | **契约与登记** | 新增 ADR-017《DID 服务契约》（库表 / 接口 / 错误码段 / 衔接口径）；ADR-015 补记（SM2 托管扩展 + 端口回环事实）；DID 服务错误码占用 **1005 段**（九位体系顺延制度，ADR 留痕登记）；新模块登记进根构建（自动纳入门禁与覆盖率统计）；公共错误码组件零改动 |
| S5 | **依赖口径** | **零新增第三方依赖**：服务间调用沿既有 `KmsKeyProvider` 的 JDK 内置 HTTP 客户端先例 |

**格式预览（业务可见，hifi 定稿）**：DID 标识建议形如 `did:ctds:<主体申请编号>`（重签产生新标识、旧标识永不复用）；DID 文档公开要素建议含 DID 标识、SM2 公钥、状态、关联主体、解析入口——**不含任何 L4 敏感信息**（法人身份证号、证照影像一律不出现）。如对标识或文档形态有偏好，请在确认时一并说明。

## 3. 主要流程（业务语言）

1. 审核员在审核工作台点"通过" → 主体状态变"已入驻"（既有能力，判定逻辑不动）。
2. 主体服务在审核**提交成功之后**告知 DID 服务"某主体已入驻"（重复告知不会造成第二份身份）。
3. DID 服务先登记一条"待签发"记录 → 请 KMS 为该主体生成 SM2 密钥对（私钥只存于 KMS）→ 组装 DID 文档 → 记录转"有效"并写入留痕四要素。
4. 若密钥服务不可用或生成失败：主体仍是"已入驻"，DID 记录停"待签发"；运营可重试，重试成功后补齐留痕。
5. 重复触发（重复点击 / 重放 / 重试）：该主体仍只有一条有效 DID。
6. （若 §3 Q4 裁 A）运营在管理页对某有效 DID 填理由 → 二次确认 → 状态变"已吊销"、立即生效、留痕五要素；不可逆，继续使用需重签（换全新密钥对）。

### 待确认问题（需要人裁决的业务选项，含建议倾向）

**Q1｜DID 能力放在哪里？**
- **A（建议）新建独立服务 `services/did`**：平台各服务"一个服务一份契约"是既有做法（KMS 服务契约 ADR-015、主体服务契约 ADR-016）；后续解析验证（3.1.9）、互认（3.1.10）、管理界面（3.1.11）都各有着落，主体服务不会被 DID 撑大。代价：演示时多启一个后端进程、多一份构件。
- B 并进主体服务：演示进程少一个，但 DID 的全部能力（含 3.1.9 解析验证与 3.1.11 界面后端）都会长在主体服务里，与 WBS 的包分工和既定的"一个服务一份契约"做法相悖。

**Q2｜演示时多个后端服务如何并存？（与演示可行性直接相关）**
- **A（建议）给每个服务固定端口并强制"只许本机访问"**：主体服务 8080（前端代理无需改动）、KMS 8081、DID 8082，启动步骤写进交付说明。代价：需在 ADR-016 的安全边界登记里补记 KMS 端口；3.1.11 界面接入时按前缀增加一条前端代理（随 3.1.11 设计）。
- B 维持"所有服务都用 8080、按需启停"：**S1 演示将无法执行**——一次"审核通过→自动签发"的业务流要求主体服务、KMS、DID 服务**同时在线**。

**Q3｜"已入驻 → 自动签发"的衔接怎么实现？**
- **A（建议）审核事务提交成功后，由主体服务调用 DID 服务的签发接口**：完全符合规格"签发失败不改变入驻状态、记录停待签发可重试"的失败隔离语义；实现最直接，无需新增机制。
- B 用"出站事件表 + 后台消费"异步解耦：解耦最彻底，但仓库目前没有这类机制，需要新增组件与调度，明显超出本包 2 会话预算。
- C 由 DID 服务定时扫描"已入驻但无身份"的主体：引入轮询延迟（演示"通过后立刻可查"的体验变差），且要为主体服务新增查询接口。

**Q4｜"吊销/重签"的写操作归哪一包？（规格 §6.1 授权由本包与 3.1.9 的设计澄清）**
- **A（建议）归 3.1.8**：DID 注册表与状态写入只有一个归属，3.1.9 只读（解析、验证、状态检查）；且与 WBS 依赖一致——3.1.11 管理页（含吊销）依赖 3.1.8，若吊销写归 3.1.9，3.1.11 会缺后端能力。
- B 归 3.1.9：与"吊销状态检查"同包，但状态读写在两包间分裂，且与 WBS 的 3.1.11 依赖链不符。

## 5. 已知风险与实施前置检查项

1. **KMS 默认配置的启动疑点**：KMS 的默认配置排除了数据库自动配置，但其数据仓储构造器依赖数据库客户端——全仓没有覆盖该配置的启动测试。实施会话第一步实测；若确认无法启动，如实登记并明确"KMS 与 DID 服务一律以 mysql 配置启动"，**不夹带非本包修复**。
2. **既有测试缺陷 DB-22 会干扰验证**：主体服务的核验次数集成测试在本地 00:00~08:00 窗口必红（测试造数用数据库时钟、服务判定用应用时钟）。实施会话若落在该窗口，须按登记口径归因并留痕，不得把既有缺陷记到本包。
3. **端口与回环变更触及既有登记**：ADR-016 §2.7 需补记 KMS 端口与本机绑定的落实状态（随本包 ADR 补记留痕）；台账 DB-03 注记同步更新。
4. **私钥零明文是硬要求**：库表、接口响应、日志三处都要有"删掉实现必变红"的锚定测试（沿既有 DB-05/DB-20 反向验证先例），否则视为未验证。
