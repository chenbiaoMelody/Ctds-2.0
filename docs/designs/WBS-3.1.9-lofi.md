## 1. 做什么 / 不做什么（逐条来自规格，禁止规格外项）

### 1.1 做什么（W1~W7）

| 编号 | 做什么（业务可读） | 规格出处 |
| --- | --- | --- |
| W1 | **解析（查身份说明书）**：凭 DID 标识可查询该身份的公开说明书（DID 文档：标识、公钥、关联主体、解析入口）与当前状态（**只两值：有效 / 已吊销**）。未登记的标识返回**明确业务答复**（"未登记"），不伪装成系统故障 | 行为 2 规则 1、3；验收标准 1、3 |
| W2 | **已吊销照常可解析**：已吊销的身份仍能查出文档，状态明确显示"已吊销"——验证方必须看得到吊销状态（W3 依赖此口径）；不提供"恢复" | 行为 2 规则 4；行为 4 验收标准 4 |
| W3 | **验证三查（签名 + 状态 + 绑定）**：某方主张"我是该身份持有者、这是我对该数据的签名"时，平台三查：① 用该身份的公钥**验签**（国密 SM2，经 common-crypto 唯一入口）② 状态为"有效" ③ 其关联主体在空间内为**有效主体（已入驻）**。任一不满足即"验证不通过"，并给出**明确失败原因** | 行为 3 规则 1、2；验收标准 1~3 |
| W4 | **解析/验证结果不含 L4 敏感信息**：说明书与验证答复中不出现法人身份证号、证照影像等敏感明文；验证请求中的业务数据原文**不留存**（验证通道不是数据存储通道） | 行为 2 规则 2；行为 3 规则 3 |
| W5 | **验证留痕三要素**：每次验证留下 时间 / DID / 结果（失败另含原因）——留痕不保存业务数据原文 | 行为 3 规则 3；验收标准 4 |
| W6 | **验证≠授权（口径声明）**：验证通过仅证明"身份主张成立"，不含任何业务授权；授权由使用控制策略与各业务模块另行管辖（本包只交付身份结论） | 行为 3 规则 4；验收标准 5 |
| W7 | **契约与登记**：解析/验证接口、1005 段顺延新错误码、验证留痕表登记于 **ADR-017 补记**；状态枚举复用既有两值（不新增枚举） | ADR-017 §2.9；ADR-005 §3.5 |

## 2. 结构组成（模块/组件）

| 编号 | 组成 | 说明 |
| --- | --- | --- |
| S1 | **扩展既有 DID 服务**（建议，见 §3 Q1） | 解析 + 验证两端点 + 验证留痕落库；四层结构与分层守卫沿用既有范式；**不新建服务**（ADR-017 §2.9：解析/验证走 DID 文档公开要素 + 注册表当前状态，同域只读能力） |

## 3. 主要流程（业务语言）

1. **解析**：某方拿 DID 标识来查 → 系统在身份注册表里找 → 找到则返回"说明书（公开要素）+ 状态（有效/已吊销）"；找不到则明确答复"该标识未登记"。
2. **验证**：某方提交"DID + 数据 + 签名" → 系统依次三查：
   - ① **签名核验**：从该身份的说明书取公钥，对数据验签（国密 SM2）；
   - ② **状态核验**：该身份当前是否"有效"（已吊销 = 不通过）；
   - ③ **主体绑定核验**：该身份关联主体在当前空间是否"已入驻"（经主体服务实时查询）。
3. 三查全过 → 结论"验证通过"；任一不过 → "验证不通过 + 明确原因"（签名不匹配 / 已吊销 / 主体未入驻或不可用，见 §3 Q6）。
4. 每次验证（无论结果）写入留痕：时间 / DID / 结果（失败另含原因）；不留业务数据原文。
5. 已吊销身份：解析照常返回（状态=已吊销）；验证一律不通过（原因=已吊销）——双向口径（行为 4 验收标准 4）。

### 待确认问题（需要人裁决的业务选项，含建议倾向）

**Q1｜解析/验证能力放在哪里？**
- **A（建议）扩展既有 `services/did`**：ADR-017 §2.9 已定"解析/验证走 DID 文档公开要素 + 注册表当前状态"——同一权威数据源（`ctds_did` 库）上的只读能力，同域扩展最直接；不引入第二个 DID 权威源；演示仍是三服务。
- B 新建独立解析服务：与 WBS"一个服务一份契约"做法表面一致，但会引入"两个服务同读一个 DID 权威库"或"跨服务再转发"的额外复杂度，且本包预算仅 1 会话。

**Q2｜主体绑定核验（三查③）怎么实现？（核心设计点）**
- **A（建议）经服务间只读调用主体服务既有查询接口**（`GET /api/v1/subject/registrations/{subjectNo}`）：实时、单一事实源；身份头沿 did→kms 先例（服务身份 + 角色映射含 `subject.read`，实施前置检查项②实测确认）。**不可达时的表征建议 = 明确"核验服务暂不可用"（不冒充"验证不通过"）**——把系统故障与"身份主张不成立"区分开，避免误导（见 Q6 原因枚举含"不可用"类）。
- B 不可达时视为"验证不通过（绑定核验失败）"：实现最省，但把"查不到"和"不是"混同，演示与生产都可能把故障读成身份无效。
- C DID 库本地缓存主体状态：违反单一事实源（ADR-017 §2.2），且需引入同步机制——超预算，不建议。

**Q3｜验证接口的访问控制？**
- **A（建议）演示期无鉴权 + 诚实边界登记**：验证是"服务间/演示期对外开放能力"，沿 3.1.8 签发面先例（回环网络隔离是真实边界；上线前由网关 + 真实令牌 + 服务间鉴权收紧，登记 ADR-017 补记与交付说明）。
- B 要求 `did.admin`/`subject.read` 等角色：演示期每个验证方都要配令牌，与"对外验证"的业务定位不符（验证方可能是外部系统）。

**Q4｜解析接口的访问控制？**
- **A（建议）演示期无鉴权 + 诚实边界登记**（同 Q3 口径）：解析结果只有公开要素，无敏感信息；对外可用性优先。
- B 要求角色：同 Q3-B 的代价，收益有限（公开信息）。

**Q5｜解析是否留痕？**
- **A（建议）不留痕**：规格只要求"每次验证留痕"（行为 3 规则 3）；解析是只读查询，留痕会放大表体积且规格未要求。
- B 也留痕：超出规格要求（章程"最小实现"）。

**Q6｜验证失败原因枚举粒度？**
- **A（建议）四类**：`SIGNATURE_INVALID`（签名不匹配/数据被篡改）/ `REVOKED`（已吊销）/ `SUBJECT_BINDING_FAILED`（主体未入驻）/ `BINDING_UNAVAILABLE`（核验服务不可用，非"不通过"之身份结论，如实表征系统态）。与规格验收标准 2/3 点名原因（签名失败/已吊销）逐条对应，并新增"不可用"诚实类。
- B 粗粒度二类（通过/不通过）：无法满足验收标准"明确失败原因"。

## 5. 已知风险与实施前置检查项

1. **SM2 验签与 KMS 签名的 round-trip**：`Sm2Service.verify(data, signature, publicKeyHex)` 已确认存在；**实施第一步实测**：经 KMS `/signatures` 端点对数据签名（DER）→ 用 DID 文档公钥（130 hex `04‖X‖Y`）验签通过——两处编码口径（DER 签名 / hex 公钥）必须实测对齐，不能凭记忆。
2. **did→subject 角色映射**：主体服务查询接口需 `subject.read` 权限；实施第一步确认服务身份头映射口径（沿用 did→kms 的"角色→权限"配置先例），并在规格允许范围内**不改主体既有鉴权行为**（只按既有权限点接入）。
3. **演示环境在跑**：三服务（8080/8081/8082 回环）+ Docker 三容器运行中（承接 3.1.8 验收环境）；实施会话可直接复用，但需重新打包 did/subject 新构件。
4. **验证接口无鉴权面（Q3-A 若采）**：后果表征（谁能验证、能验证什么、解除条件）必须写入 ADR-017 补记 §安全边界 + 交付说明（沿 3.1.8 评审②P2-2 先例），演示机须为可信机器。
5. **验签失败与"数据被篡改"的表征**：规格验收标准 2 要求"签名核验失败"原因——实现中验签异常（如签名格式非法）也须收敛为同一原因类（不得直出 500），**边界值**（空数据/非法 Base64/超长输入）在 hifi §边界值表定稿。
