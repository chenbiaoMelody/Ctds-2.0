## 3. 主要流程（业务语言）

1. **看空间**：打开左侧菜单「逻辑空间」→ 默认列出我能看到的空间（分页）→ 可按名称检索 → 每行显示名称、场景类型、参与方范围、可见性、状态、生效期 → 点行进入空间详情。**看不到的空间**（我既不是成员、也不是平台运营方、且空间不公开）不会出现在列表里，直接打开其地址也只会得到统一提示（后端按"不存在"口径同形返回）。
2. **建空间**：点「创建空间」→ 填名称、场景类型、参与方范围、可见性（简介与生效期可选）→ 提交 → 成功则新空间出现在列表且状态为"已创建（未启用）"，我是所有者；未入驻主体提交会被拒，界面**原样展示统一业务文案**（不会提示"该主体不存在"）；同名或"只差首尾空白"的重名会被拒。
3. **管生命周期**：进入详情概览 → 按状态给出"启用 / 冻结 / 恢复 / 解散"→ **解散**先弹窗二次确认，文案明示"解散后不可恢复"，选"取消"什么都不会发生（不发起请求），选"确认"后状态变为"已解散"且不可再回到其它状态；无权限时界面**如实展示后端拒绝文案**（不在前端伪装成成功/失败）。
4. **改配置**：概览区"修改配置"只允许改简介与生效期，其余字段不提交；保存后可见变更结果。
5. **管成员与准入**：详情"成员与准入"区 → 邀请制空间发邀请（被邀方"我的邀请与申请"里确认后才成为成员）；公开/审批制空间由申请人提交申请、管理员审批（拒绝须填理由）；成员列表可授予/收回管理员、移除成员（理由必填）；成员可主动退出；所有者可把所有权转移给某位成员。**所有"越权"动作以后端拒绝为准**——界面隐藏不算权限。
6. **配策略**：详情"策略"区一屏看到该空间**有效策略**（每行标注来源：继承自平台 / 空间级生效 / 空间覆盖未生效（取严））→ 对某条目提交覆盖 → 红线条目放宽会被拒（原样展示拒绝文案，有效策略不变）；冻结期调整会被拒；已解散空间只能查看不能改。
7. **平台治理**（平台运营方）：左侧菜单「平台策略治理」→ 查看平台级条目 → 新建条目或改值与红线标记（键不可变更）。
8. **留痕核对**：概览区"操作留痕"列出该空间的动作记录（谁 / 何时 / 做了什么 / 结果 / 理由 / 从何值→到何值），不含任何敏感原文。
9. **切换演示身份**（演示期）：顶栏设置"当前操作主体编号"与"身份档"→ 换主体即可扮演剧本中的 A / B / C / D / E 主体；切到"平台运营方"档即可执行治理类动作（治理解散 / 查看他人空间治理信息 / 平台策略治理）。

### 待确认问题（需要人裁决的业务选项，含建议倾向）

**Q1｜本包界面范围与菜单结构？**
- **A（建议）两个菜单项 + 一个空间域内的个人页**：「**逻辑空间**」= 空间列表 / 创建 / 详情（概览 + 成员与准入 + 策略）；「**平台策略治理**」= 平台级条目治理；「我的邀请与申请」= 空间列表页内的入口页（不占菜单项）。理由：与 WBS 行 256"空间管理 / 成员管理 / 策略配置页面"三块一一对应（后两块在空间详情内，天然带空间上下文）；平台策略治理属平台域（权限点 `platform.policy`），独立菜单与治理例外口径一致。
- B 三个独立菜单项（空间管理 / 成员管理 / 策略配置）：成员与策略脱离空间上下文，必须先选空间再操作（多一跳），且与剧本"进入空间详情某区"的表述不符。
- C 只做 WBS 行字面三页、不做平台策略治理页：3.2.5 承接项③（平台条目治理页）无落点，C-2.3 剧本演示前"平台策略与红线条目就绪"无法在界面自查。

**Q2｜"演示身份"（主体 + 档位）切换放哪里、带不带平台运营方档？**
- **A（建议）顶栏全局控件 = 主体编号（必填）+ 身份档（普通主体 / 平台运营方）**：主体编号写入既有 `ctds-demo-subject`；空间域请求按档位设置角色头（普通档 `applicant`／运营档 `applicant,platform.operator`）。理由：① 剧本要求在**同一场走查内在多主体间切换**（C-2.1 S1-1 以 C 主体被拒、S2-5 以 B 主体越权、C-2.2 S1-2 以 B 主体确认邀请、S2-5 以 E 主体越权等 ≥6 步）；② C-2.1 S3-7、C-2.3 S1-5/S3-6 需以平台运营方身份操作；③ **越权类步骤要求请求不带 `platform.operator`**——若恒带该角色，成员越权会被服务端放行，剧本"越权被拒"步骤将误判为缺陷（此为硬约束，非偏好）。
- B 只在空间页页内切主体、运营档只落在「平台策略治理」页：C-2.1 S3-7（运营方在空间详情冻结）与 C-2.3 S1-5（运营方查看空间 B 治理信息）无法界面走查 → 这两幕需改由技术侧配合（剧本操作列须经 PO 批准修订）。
- C 不做切换（靠改本地存储或技术侧代发请求）：界面对"多主体对照"完全无承载能力（≥6 步），"可演示"不成立。

> 补充事实（设计约束，非选项）：`common/auth` 的 `AuthContextFilter` 在 **`X-Ctds-Subject` 为空时整头作废（按未认证）**，角色头一并不生效 → 主体编号必须必填，界面前置拦截空值。

**Q3｜列表 / 详情 / 成员 / 准入的数据源与展示口径？**
- **A（建议）全部复用既有只读端点、只展示空间域自有数据**：列表 `GET /api/v1/data-spaces`（分页 + `keyword` 名称前缀）；详情 `GET /api/v1/data-spaces/{id}`；成员列表 `GET /{id}/members`（**行级 `memberId`** 是角色变更/移除/转移的必要定位）；准入列表 `GET /{id}/admissions`（分页 + `status`）。展示只到"主体编号"层，**不跨服务取主体名称**（最小暴露）。非成员打开非公开空间时，后端已按"不存在"同形返回 → 界面用**同一条**统一提示样式（不区分"不存在 / 无权"），与后端防枚举口径一致。
- B 详情页直接用 `GET /{id}` 的内联 `members`（仅 subjectNo + role）：缺 `memberId`，3.2.4 的行级端点（角色变更 / 移除 / 转移）无法定位目标行 → 不可行。
- C 跨服务拼接主体名称展示：需扩展服务间契约（暴露面扩大），收益仅"更好看"。

**Q4｜「我的邀请与申请」的入口形态？**
- **A（建议）空间列表页内入口 → 独立页 `/spaces/my-admissions`**（不占菜单项），承载 `GET /admissions/mine` + 确认 / 谢绝（`POST /{spaceId}/admissions/{admissionId}/confirmation`）。理由：C-2.2 S1-2 要求"以 B 身份进入我的邀请确认"，而**此时 B 还不是任何空间的成员**（进不去空间详情，非成员只能看到公开摘要）。
- B 放进空间详情"成员与准入"区：被邀方在确认前无法打开该空间详情 → 步骤走不通。
- C 不做，改由技术侧配合：C-2.2 S1-2 的界面步骤落空（剧本需 PO 批准改操作列）。

**Q5｜生命周期动作与配置变更的交互形态？**
- **A（建议）按钮 + 二次确认（解散强制）**：启用 / 冻结 / 恢复 = 按钮 + 结果提示；**解散** = 弹窗二次确认（明示"解散后不可恢复"）→ 取消 = **不发起任何请求**；确认 = 提交 `{confirmDissolve: true}`（后端 `1006C0006` 兜底缺确认）；配置变更 = 表单**仅提交简介 / 生效期白名单字段**，其余只读展示；全部拒绝文案原样展示（`1006C0002` 状态不允许 / `1006C0006` 缺确认 / `1006C0007` 无权限 / `1006C0004` 空间不存在）。
- B 一步式（点"解散"即提交）：无法满足剧本 C-2.1 S3-4"二次确认 + 明示不可逆"的验收，且规格行为 2 规则 4 明示二次确认强制。
- C 前端先自行判断"能不能做"再隐藏按钮：界面隐藏不构成权限（规格行为 4 规则 3），会把"越权被拒"步骤变成"看不见"，掩盖服务端判定 → 只用状态做**体验层提示**，判定一律以后端为准。

**Q6｜是否为"空间操作留痕"新增一个只读端点？（承载 C-2.1 S1-3 的界面核对）**
- **A（建议）新增 `GET /api/v1/data-spaces/{id}/action-logs`（只读）**：分页返回该空间留痕（动作 / 操作者 / 时间 / 结果 / 理由 / 从何值→到何值）；权限 = 空间成员或 `platform.operator`，`DISSOLVED` 空间仅 owner / `platform.operator`（与"有效策略视图"同口径）；**零新增错误码**（复用 `1006C0004` / `1006C0007`）、**零新增库表 / 迁移**（只读既有 `space_action_log`）、**零改动既有端点语义**（沿 3.1.11 先例：界面卡只加"读"端点）。理由：C-2.1 S1-3 的操作是"打开空间详情查看留痕"、判定是"创建留痕含四要素"，当前无任何读端点可承载 → 不加则该步无法界面走查（剧本需 PO 批准改操作列）。
- B 不加，留痕核对改由技术侧配合（C-2.3 S1-6 / S2-6 已注明技术侧配合，C-2.1 S1-3 需同步改口径）：交付更小，但 C-2.1 剧本 19 步中有 1 步的界面路径不存在。
- C 用"详情页的创建时间 + 所有者"替代留痕：只能证明"创建时间/创建者"，**证明不了"留痕四要素"**（行为 1 规则 4 的验收标准）→ 判定不成立。

**Q7｜前端角色头与菜单权限点口径？**
- **A（建议）页面级角色头 + 菜单权限点按域命名**：空间域请求的角色头在 `api/space.ts` 内按"演示身份档"设置（普通 `applicant`／运营 `applicant,platform.operator`），**不改** `client.ts` 的全局 `demoRolesHeader()`（避免把 `platform.operator` 带到其它服务的调用，最小权限面——沿 3.1.11 Q7 先例）；菜单权限点：「逻辑空间」`space.member`、「平台策略治理」`platform.policy`（演示期 admin 角色可见；普通 user 角色不可见 → 菜单计数 admin 8→10、user 5 不变）。
- B 改全局角色头：`platform.operator` 会随所有页面请求发出（权限面扩大），且在空间域之外的接口上也可能命中映射 → 不建议。
- C 空间菜单不设权限点（登录即可见）：服务端仍会拒（`1006C0007`），但菜单对无权限角色可见会造成"看得见做不了"的困惑，且演示期审计口径不清晰。

**Q8｜策略配置区的交互形态？**
- **A（建议）有效策略表格（只读）+ 覆盖提交表单**：表格列 = 条目名称（`displayName`）/ 生效值 / **来源标注**（继承自平台 / 空间级生效 / 空间覆盖未生效（取严））/ 平台值 / 空间值 / 说明 / 红线标记；覆盖提交 = 选条目（目录三键）+ 选值（该键封闭值域下拉）→ `POST /{id}/policies/overrides`；放宽被拒（`1006C0013`）**原样展示**且表格不变；冻结/解散态按后端返回如实展示（`1006C0002` / `1006C0014`）。
- B 只做只读有效策略视图：C-2.3 S2-2/S2-3/S2-4（"放宽被拒"与"收紧生效"）无界面落点。
- C 前端先算"严不严"再拦：策略目录与取严规则是后端权威（`PolicyCatalog` / `EffectivePolicyResolver`），前端复算 = 两处各自定义策略模型（规格行为 7 规则 6 禁止）→ 前端只做值域下拉，**不做放宽判定**。

> 说明：本包的四个界面面（空间 / 成员与准入 / 策略 / 平台治理）**共享同一套 API 模块、常量、身份切换与详情页**，拆分会产生同文件反复改动窗口；且三份剧本是**同一业务域的三幕**，拆分将使 C-2.3 的"策略面"走查无法与空间面同批验收。

**已知风险**：
1. **越权步骤与角色头相互影响**（Q2/Q7）：若角色头口径写错（恒带 `platform.operator`），"越权被拒"类剧本步骤会被服务端放行 → 必须由**测试锚点**钉死"普通档不带 `platform.operator`"（hifi §7），并在走查前确认档位默认值 = 普通主体；
2. **演示身份写在浏览器本地**：同一演示机换人操作需重置，走查步骤卡须写明"第几步切到哪个主体"（演示材料随交付给出）；
3. **剧本界面名称漂移**：三份剧本均写"待 3.2.6 交付后核对修订" → 交付后必须一次性核对修订并提示 PO 批准，否则执行人找不到入口；
4. **"看得见 vs 做得了"不一致**：演示期 admin 角色可见菜单，但以某主体身份执行时可能被后端拒绝（越权被拒正是剧本要求）→ 界面必须**如实展示后端文案**，不得改写或吞掉；
5. **非成员同形提示**：非公开空间对非成员按"不存在"口径返回，界面两条分支必须用**同一个**文案与样式（防存在性探测口径一致），不得前端区分。
