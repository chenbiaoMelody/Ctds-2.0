## 1. 目的与使用方式

1. **一句话目的**：把等保三级的每一项要求，对照到本项目的"哪份设计、哪段代码、哪个证据"，让"是否满足等保"从一句口号变成一张可逐行核对、逐行补齐的账。
2. **三类读者**：
   - **人（PO / 安全与合规专员）**：看"状态"列和 §6 缺口清单，掌握"已有什么、缺什么、缺口去了哪个任务"；
   - **AI 会话**：做任何新任务前按本文档核对所涉及控制项的当前状态，交付时刷新相关状态行；
   - **外部测评机构（未来）**：按"证据锚点"列快速取证。
3. **与既有制度的关系**：本文档即章程发布检查单（章程 12.1）中"等保自查清单"的实体化；安全红线（AGENTS.md §2 第 7 条、§3）是本清单落地手段中"强制门禁"级别的子集。

## 2. 范围与口径

- **标准范围**：GB/T 22239-2019 第三级**安全通用要求**（技术要求 5 族 + 管理要求 5 族），控制点粒度（二级标题层）。云计算/物联网/移动互联等扩展要求暂不展开（部署形态为单机演示集群，生产上云后按扩展要求增补，登记见 §6）。
- **物理环境口径**：本项目为纯软件平台，不拥有机房。安全物理环境一族整体归入"部署环境责任方"（演示期 = 本机 Docker Desktop；生产期 = 政务云/IDC 服务商），逐点标注"范围外（环境责任）"，仅保留对外部环境的准入要求登记。
- **状态图例**：

| 标记 | 含义 |
| --- | --- |
| ✅ 已实现 | 有运行中的实现且有可复核证据（测试/脚本/现场） |
| 🟨 组件基座 | 公共组件/清单已存在并经测试，但业务侧尚未成体系接入（骨架期的正常形态） |
| 📘 契约已定 | ADR/设计文档已批准并留痕，实现未落地 |

| ↗ 范围外 | 归外部责任方或后续形态处理，已登记说明 |

## 7. 贯穿执行与维护规则

1. **谁来更新**：每个 AI 会话在交付涉安全任务时，刷新本文档相关控制项的"状态"与"证据锚点"列（随任务分支提交），并在开发日志声明"等保映射已刷新：××控制项"。
2. **何时复核**：① 里程碑前按章程 12.1 将本文档作为等保自查清单全量走查一遍；② 每季度随风险登记册刷新（风险对策手册 §季度事项）。
3. **缺口管理**：G 系列编号一经分配不复用；缺口补齐后该行标记"已闭环（任务号/日期）"，行保留作追溯。新增缺口必须先入 §6 再散落描述。
4. **禁止事项**：禁止为让清单变绿而虚报状态或伪造证据锚点——状态只有对得上证据才算数（对应章程"绿灯不失真"原则）。
