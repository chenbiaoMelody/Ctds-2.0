### 问题与教训

1. **测试环境组件行为断言必须先做反向探针**：本包 F1 首验时"必填拦截"在 jsdom 下完全不渲染红字——不是组件问题，是 element-plus 被 vitest 外置后 async-validator 导入互操作坏了，TypeError 被 EP 吞成"校验通过"。症状与"业务代码 bug"同形，极易误判。教训：写"必填拦截/校验"类断言前，先"故意留空点击提交"确认红字真的会出现，否则该锚从未生效（已入记忆）。
2. **接口契约核实落到 Controller 出参层**（3.1.5 教训延续）：本包 T2 初稿按应用层猜了 HTTP 信封形状，核对冻结契约后更正为 HTTP 400 + 1000C0001。
3. **红锚突变要用"等价破坏"而非"SQL 占位符错配"**：第一轮 T5 突变把 `AND status=?` 删了但留着 4 个参数导致 SQL 参数错配（红的形态不对）；改 `AND status IS NOT NULL` 等价恒真后才锚到真正的门槛语义。
4. **git checkout 会连带冲掉同文件的合法改动**：本会话两次 `git checkout --` 误伤 S1/RegisterView 合法改动，靠重新施加救回——教训：还原突变用 python 精确反向 patch，不要对含合法改动的文件整文件 checkout。
5. **演示环境幂等缓存与 TRUNCATE 交互**：联调脚本 TRUNCATE 业务表但内存幂等缓存未清（mode=memory），跨轮重跑会复用已删除的旧申请编号 → 上传报"申请编号不存在"；解决办法 = 重启后端清缓存 + 脚本开跑前清库 + 动态捕获主体号，走查脚本自包含后 14/14。
6. **i-dempotency 计时敏感用例是存量 flake**：与插桩/负载相关，无插桩标准门禁稳绿；已登记观察项而非混入本包修复。
