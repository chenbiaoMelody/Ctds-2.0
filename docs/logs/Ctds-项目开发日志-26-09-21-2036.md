### 问题与教训

1. **测试自证"覆盖了并发"但实际是假断言**：原 `issueTwiceIsIdempotentSingleActive` 把幂等归因于内存桩的线性"先查后建"，完全不经并发窗口；而仓储层 `completeIssuance` 无状态门槛 → jacoco 显示该分支零覆盖。**教训：并发/幂等断言必须锚定真实竞争窗口（交错用例/多线程用例），并核验 jacoco 关键分支非零覆盖——"测试存在"不等于"断言为真"。**
2. **评审③④同根发现不同视角**：③（一致性）发现"completeIssuance 与 revoke 不对称"，④（测试质量）发现"0 行分支零覆盖"——同一缺陷从两个视角汇聚，说明对称性缺失 = 测试盲区的可靠信号。**教训：仓储写操作的"对称性"（同型操作门槛一致）应作为自检项。**
3. **HTTP 客户端先例同构要连测试一起对齐**：补 `statusCode` 校验后，既有桩测（期望 400+业务码被抛出）变红——先例（KmsKeyProvider）本就是 statusCode 优先。**教训：与先例对齐时同步对齐测试语义（业务码分支改为 200+非 0 code 触发），避免新旧口径并存。**
4. **配额降级 → 补派 → 打回 → 修复 → 重交的完整闭环**：③④上次降级自检（结论通过），本次独立补派后④打回——降级自检的"通过"结论被独立评审修正。**教训：降级自检只能作为临时留痕，独立评审的修正价值真实存在；打回后按门禁无特批直接修复重交，不争论。**（本会话评审派发未再遇限流。）
