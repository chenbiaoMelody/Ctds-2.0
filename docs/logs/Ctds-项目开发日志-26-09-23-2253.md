### 做了什么（业务可读）

"身份查验服务"已经建成并通过全部本地检查。具体是：**解析**（凭身份编号查公开说明书与状态"有效/已吊销"，查不到明确答复"未登记"）；**验证**（三道检查：签名对不对 → 身份是否有效 → 其主体是否已入驻，全过才"验证通过"，并给出四类明确失败原因）；**每次验证留痕**（时间/身份/结果/原因，不存被验证数据原文）。过程中发现并解决一个真实的设计缺口：原计划复用"查主体信息"的既有接口来核对"是否已入驻"，但那个接口有防探测保护（不允许服务身份直接读任意主体）——已改为**新增一个只读状态接口**（只回"编号+状态"两个字段），既满足查验需要，又不放宽原有安全口径。全部功能已用真实密钥签名、真实服务调用端到端演示通过；所有自动检查（编译、单测、规范、安全扫描）绿灯。

### 问题与教训

1. **跨服务复用的"两层门槛"必须先实测**：既有查询端点既有功能级权限（`subject.read`）又有对象级归属断言（防枚举）——只配权限点不够，第二层会把服务身份拒掉。**教训：复用他人端点的前置检查必须端到端实测（含 200 路径），并把"发现不可行 → 最小暴露新端点"作为标准处置。**
2. **门禁超时红灯的归因要量化**：首跑红灯文案"mvn test timed out"易误读为测试失败——实测全仓 595s vs 上限 600s（BUILD SUCCESS）才定性为"规模顶上限"。**教训：超时类红灯先量时长再处置；处置只走"压缩自包开销"（不碰门禁配置/他人模块），结构性矛盾登记债务。**
3. **测试类合并是可用但需留痕的手段**：合并省容器启动（-46s）但改变了测试类布局——已在类注释、自检单、台账如实注明理由（门禁时长合规），供评审核查。
4. **环境脆弱性（Docker 两度掉线）**：编码期 Docker Desktop 两度停止（容器连带不可达 → 服务进程退出）——重启即恢复（数据保留），但暴露"演示环境依赖 Docker 引擎稳定性"的运维注意点。
