### 问题与教训

1. **"共享权限点 = 对既有角色开放"**：内部服务端点复用通用 `subject.read` 时，权限面实际覆盖了申请人/审核员——评审②与①独立命中。**教训：内部面权限必须专用化（专用权限点 + 仅授服务身份角色），并在测试中显式断言"既有角色被拒"。**
2. **"形似成功"的系统响应不得当业务通过**：非 200 + `code=0` 的 body 会被误判"已入驻"——这是把系统态冒充业务结论的反向错误（比"把故障当失败"更危险）。**教训：先判传输层状态码，再判业务码。**
3. **承诺必须有可证伪的锚定**：映射表两处"声称的断言"实际不存在（缺字段集断言、解析侧无反向探针）——**教训：任何"仅含 X 字段/绝不含 Y"的承诺，必须同时具备正向断言 + 植入样本反向探针，否则不写进映射表。**
4. **文档引用要落地核对**：`ADR-005 §3.5` 是错引（顺延制度在 ADR-006 §3.5）——三处同错传播。**教训：引用编号类断言，落盘前抽查 ADR 目录实际章节。**
5. **评审期实测发现演示环境已停**：netstat 无 8080/8081/8082 监听（`-2258` 时三服务在运行）——验收前须重启；`@Value` 松散绑定疑点（②P3-1）已通过"配置显式声明"从根上消除（占位符按 env 名精确匹配）。
6. **DB-25 相关**：本次修复新增 5 例（did 单元 3 + did 集成 2，集成分摊于既有容器，时长增量秒级），门禁时长仍贴上限——结构性矛盾未消，DB-25 待裁决。
