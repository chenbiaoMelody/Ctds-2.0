### 问题与教训

1. **复合长命令中的复杂格式串会"静默失败"**：首条组合命令（`git merge` + `git log --format="%H%n%s%n…"`）在 PowerShell 下报"系统找不到指定的路径"且**无任何 git 输出**——看上去像"合并失败"，实际上**合并根本没有执行**（已用 `git log/status` 回查确认 main 仍 `5700610`）。拆为最小命令后一次成功。教训：① 关键动作（合并/推送）**不与其他命令混在一条复合命令里**，避免"命令未执行"被误读为"操作失败"；② 失败后先回查真实状态再重试，不盲目重跑。
2. **日志记载的分支 HEAD 可能滞后**：`-2245` 日志第 7 条只列到 `f1b5201`，实际分支 HEAD 为 `606696b`（22:45 验收留痕提交）。教训：合并前必须回读 `git log --oneline` 以**仓库为准**，不采信日志列表的完整性假设（同族：`-2003`"文档引用编号要落盘后抽查"）。
3. **先例冲突时"不代选"**：`fix/*` 分支在合并后是否清理，卡 1 先例是删除、DB-22 先例是保留——两者矛盾时按红线 2 上报为待裁决项，不擅自删远端分支（删除远端属高影响动作）。
4. **同一事实两个数字必须就地互指**：DB-25 有 `241s`（修复轮）与 `250s`（交付态终跑）两个口径，本会话在快照与债务行统一写 **241~250s** 并注明各自含义，延续 DB-25 评审③ 的口径纪律。
5. **合并会话的边界要守住**：本次极易"顺手"做掉的相邻事项（DB-26 裁决、3.1.10 立卡、分支清理、关停演示环境）全部**明确不做**，只留待裁决清单——合并会话越"干净"，主线历史越好审计。
