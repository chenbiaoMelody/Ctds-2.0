### 问题与教训

1. **含空格路径的进程启动（踩坑）**：`Start-Process -ArgumentList '-jar', $path` 会把 `e:/AI Projects/...` 按空格拆开 → java 报 `Unable to access jarfile e:/AI`。**修法**：把参数拼成单个字符串并对路径加引号（`"-jar \`"$jar\`" --spring.profiles.active=mysql"`）。**教训**：本机所有 java 启动脚本都要按此写法。
2. **vite dev 在前台 stdin 关闭时会退出（踩坑）**：`cmd /c npm run dev > log` 方式启动后 vite 报告 ready 却随即消失；改用 `Start-Process` + 重定向 + `npm run dev < nul`（显式脱离 stdin）后常驻。**附带发现**：vite 默认监听 `localhost` → 实测为 **IPv6 回环 `[::1]:5173`**，用 `127.0.0.1:5173` 探测会误判为"未启动"，**访问请用 `localhost`**。
3. **重签是幂等的（关键口径）**：主体已有有效身份时，重签**直接返回该有效身份**（不新建、不复用旧密钥）→ 选项 A 必须先"吊销旧有效身份"再重签。**教训**：涉及"生成新密钥对"的演示准备，必须核验返回的 `did`/`issuedAt` 是否为新值（本次第一次调用就是返回旧值，由此识别出幂等）。
4. **代签入参语义 = 明文**：`demo-signatures` 的 `data` 是待签**原文**（响应里的 `data` 才是 Base64）。首次按 Base64 传参 → 签名能生成但验证稳定 `SIGNATURE_INVALID`。**教训**：接口冒烟不能只看"是否 200"，要用"验签/反证"闭环（本次正是靠"改一字必失败"这条反证才把入参语义辨清）。
5. **验证三查含"主体绑定"**：DID 记录若无对应 subject 记录 → 必然 `SUBJECT_BINDING_FAILED`（`1000C0003` 口径）。**教训**：挑选演示/走查目标时必须选"有主体"的记录，否则会误判为功能缺陷。
6. **KMS 根密钥是本环境的"单点"**：它在仓库外临时文件里，**重启 KMS 必须沿用同一把**，否则本次生成的新密钥材料又会不可解密（已作为交接项写入材料与台账）。
