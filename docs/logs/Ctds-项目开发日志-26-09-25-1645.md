### 问题与教训

1. **测量用构建会破坏运行环境（本次真实踩坑）**：为准备覆盖率测量执行 `mvn -pl services/did -am install -DskipTests`，其 `repackage` 与**运行中**的 did 服务争用同一 jar（Windows 文件锁 → `Unable to rename` 失败，但新 jar 已写入同路径），导致运行实例后续加载的类抛 `NoClassDefFoundError`（联调首轮互认接口全部 `1000S9999`）。**定位方式**：从服务日志栈精确读到缺失类名，而不是凭猜测改代码。**处置 + 教训**：停机 → 重建 → 按既有演示口径重启（未动 KMS、演示根密钥沿用）；**今后测量构建必须先确认目标模块无运行实例**（或使用跳过 repackage 的等价手段）。**这条教训已写入 hifi §11-2。**
2. **"不能改 pom"的边界要用等价手段绕，不得破界**：PIT + JUnit 5 在 Maven 插件路径下必须改 pom（禁止）→ 改为**纯临时 CLI**（jar 只落忽略目录）→ 既拿到真实数字，又保证"零新增依赖、零门禁改动"。**教训**：边界内拿不到数字时，先找**等价且不落库**的工具路径，再考虑降级登记。
3. **"测试补全"不等于"用例数量堆高"**：13 项里有 10 项以**强化既有断言**落地（体量因此低于立卡预估），但每项都过了"删锚必红"验证——**质量证据是"能变红"，不是"加了多少行"**。**教训**：体量低于预估时要在任务卡如实说明原因（本卡已登记 §六）。
4. **测量口径要"主动申明缺口"**：`DidManagementQueryService` 在该口径下无变异覆盖——如实登记 + 给接入建议，比"挑好看的数字汇报"更符合"绿灯不得失真"。**教训**：凡"工具口径导致的缺口"，一律显式标注并给出后续处置。
5. **真实环境不制造脏数据**：`SUBJECT_BINDING_FAILED` 与"待签发重试"两分支在真实环境没有对应数据，**不造**（避免污染演示库与验收观感），由自动化用例承载并登记口径。
