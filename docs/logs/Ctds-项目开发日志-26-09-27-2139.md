### 问题与教训

1. **"实现必须与既有守卫自洽，否则等于空转"**：R3 直接 `push('/login')` 会被登录守卫弹回工作台——**任何"引导类"改动都要先读守卫/拦截链**，否则交付的是"看起来做了、实际无效"的代码（比没做更危险：它骗过评审）。教训固化：涉及跳转 / 拦截 / 权限的改动，提交说明必须写清"与守卫的交互结论"；
2. **测试先行的价值在"红"，不在"先写"**：本次用 `git stash` 制造红态，一次性证明 11 条用例都在真验东西；若不测红，很可能写出"实现缺了也照样绿"的假护栏（本项目 R1 死代码、R6 承载缺口都是这类问题的反面教材）；
3. **禁用态测试的边界**：`disabled` 按钮在 jsdom 中不派发 click，故"点击后零请求"是**弱增强**（真正的保证是 `disabled` 属性本身）；已在任务卡 §七 7.6 说明，避免下次误以为是强断言；
4. **既有用例的 fixture 变更必须"保持原断言意图"**：R2 落地后，"收回管理员取消 = 零请求"用例的目标行必须改成他人行（本人行已不渲染按钮），改的是**目标行**、不是断言——这类修改要在用例标题与注释中写明原因，并主动向评审员披露；
5. **"口径张力"要用勘误收口，不要靠"下次再议"**：本轮把 §6.6.4 与 §6.7 D（E4）、§8.9 引导登录（E5）、§8.6 文案示例（E6）一次性写死，避免后续每轮评审重复争论同一件事；
6. **跨模块的重复实现不擅自合并**：`labelOf` 在 `constants/did.ts` 与 `constants/space.ts` 各一份，S1 只要求空间侧收口；合并会动他人模块 → 登记债务、由编排师裁决是否立卡，守"不碰他人模块"的并行纪律。
