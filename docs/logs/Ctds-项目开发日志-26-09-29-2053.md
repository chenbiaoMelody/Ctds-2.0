### 做了什么（业务可读）

1. **修好了"解散后同名重建假成功"**：此前空间解散后，用同一个名字再创建，界面说"创建成功"，实际返回的是那个已解散的旧空间。根因是"防重复提交"的缓存命中后**直接把第一次的结果拿来用**，没有再核对"这个名字是否已被解散锁定"。
2. **修法（你选定的方案 A）**：创建返回后**再查一次该空间的当前状态**——已是"已解散"就按名称锁口径拒绝（提示"空间名称已被锁定，不可复用"）。没解散的重放照旧返回首次结果（防重复提交的本意不变，剧本 S1-7 不受影响）。
3. **评审环节**：四个独立评审都通过、零必修项。期间根据评审意见做了一次更精准的调整（R1：核对信号从"锁名登记表"改为"该空间自己的当前状态"）——否则别人的同名空间被解散时，你自己活着的空间重放会被误报"名称已被锁定"。
4. **真机复验（关单条件）**：重建了正式安装包、重启服务后，按剧本 S3-6 走了一遍——界面重建同名空间时弹出的正是"空间名称已被锁定，不可复用"，库里也确认没有新建空间、没有新的创建留痕；"重复提交返回首次结果"（S1-7）也复验保持。

### 问题与教训

1. **幂等命中返回的是"创建时快照"**：服务层返回值不反映其后状态变化（HTTP 响应的实时性来自控制器按 id 重读）——凡"命中后须按现状判定"的场景，必须重读当前行，不能信任缓存对象；
2. **判定信号要选"自己那行数据"而不是全局登记表**：以名称锁表为信号会把"别人的同名空间被解散"错套在自己头上（误拒 + 跨主体信息泄露）；评审①进一步论证锁表信号与规格规则 5 明文冲突；
3. **评审子智能体限流的处置**：大上下文续跑两次撞 tpm/rpm 限流（等窗重试无效）→ 改派轻上下文全新独立评审员做增量复核，独立性不降、通道恢复；单发串行纪律维持；
4. **交付态构件要与"被复验的提交"对齐**：R2 虽为零行为面（注释/文档），仍在 HEAD 重建构件并终验，避免"复验构件 ≠ 最终提交"的质疑面；
5. **环境不稳定登记**：本会话 java 服务两次无外部可见原因退出（Docker 正常）——后续会话开工先核端口，勿把"服务不在"误判为代码回退。
