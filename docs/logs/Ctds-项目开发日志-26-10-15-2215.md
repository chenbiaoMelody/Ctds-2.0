### 二、业务可读总结（给项目主导者）

1. **这一包是干什么的**：上一条主线（合约与使用控制）已经全部做完并合入主线；按计划顺序，**下一条主线是"数据交付与数据沙箱"**。本包不写代码，只做两件事——**把这一块业务规则写清楚（规格），并写成您能照着点的验收剧本**。
2. **一句话业务口径**：**只有已签好并生效的合约才能取数**；**API 调用一律走平台网关**（网关里先查合约允许不允许、再计数、再放行）；**文件交付一律国密加密后给**；**需要把原始数据交给需求方做开发时走"沙箱"——数据进得去、带不出来，产物必须经平台审核通过才能导出**。
3. **为什么要沙箱审核**：这是需求原件（产品需求文档）的原话要求——"原始数据不出域，结果审核后导出"。所以本包把"导出"设计成**唯一出口**：没审核、审核被驳回、或者绕过界面直接调接口，**一律被拒**；而且**审核通过也不等于免策略**（导出前还要过一遍合约约定的用途/域限制）。
4. **诚实边界（先说清楚，不做过头承诺）**：本包的沙箱是**平台内部的隔离环境**——"数据带不出沙箱"是硬保证；但**"数据物理上完全不出机构"** 要靠后续的连接器与隐私计算（都还没开工），本包不承诺。另外 API 调用的"密钥（API Key）签发"这轮不做（登记为未定义项），先用"合约编号 + 身份"的方式演示。
5. **本包交付了什么（可核对）**：① 规格草案 V0.9（7 条业务行为、37 条验收标准、明确 9 项"不做"、7 条边界声明）；② 两份验收剧本草案——**C-5.1 数据交付**（三幕：API 交付 / 文件交付 / 越权与绕过被拒）与 **C-5.2 数据沙箱**（三幕：申请开通 / 沙箱内使用与结果审核 / 结果导出与绕过被拒）；③ 任务卡（含映射表、体量登记、纪律声明）；④ 台账更新。
6. **验证与演示**：本包是纯文档包，**本地无代码可跑**；验证方式 = 口径与来源逐条可核（每条业务规则都能追到产品需求文档与工作分解表的具体行）、剧本步骤可逐步执行（演示前提已在剧本里写清：先跑完合约域剧本拿到"已生效合约"）。**本包不涉及任何数据与环境动作**。
7. **需要您决定的九个点（一次确认即可，建议口径都是 A）**：① 取数凭据 = 生效合约（不搞"订单"第二套凭据）；② API 交付走网关、链条里先判定策略再放行、本轮不做 API Key；③ 文件交付国密加密、记录里不落数据本体；④ 每次交付都留一条"交付记录"（后面计量与存证都用它）；⑤ 沙箱 = 平台侧隔离环境（不做跨机构承诺）；⑥ 结果导出唯一出口 = 审核通过（且仍需过策略、绕过界面也拒）；⑦ 策略判定/计量/存证三件事只"用"不"另造一套"；⑧ 命名与错误码段用第 1009 段（已核实未占用）；⑨ 剧本里的界面名字先占位、等界面包做完再一次性核对。**另外确认体量不拆分**。
