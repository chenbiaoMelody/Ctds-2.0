## 业务可读总结

**这一包现在能证明什么**：四个真实业务动作（入盟、签约、交付、使用）在同一套真实服务上依次跑完，每个动作都恰好在存证链上多出一条记录，记录里的单号和上游单据一字不差；链断了会留下"上链失败"的记录（不假装成功），链恢复后点一次重试就转成"已上链"，且不会多出第二条；审计读面上的四个环节计数、单号唯一性、按主体+时间检索，都能跟这四笔动作逐条对上。

**这次做完了什么**：写好了唯一的探针脚本（18 条判定，任一条失败就报错退出），并跑出 **18 条全过**的判定表。过程中发现并纠正了四处"设计写得跟程序不一致"的地方：入盟单号里用的是准入单编号而不是主体编号；入盟前要先有 DID（且老 DID 记录内部查不到）；只有"公共数据授权类"合约才会写授权环节，普通 API 调用类不写；交付环节的判定要补一条类型校验才能凑齐每链 3 条。这些都写进了设计的勘误表。

**顺带发现的环境坑**：昨天留着的四个服务实例没有带"存证服务地址"等配置，业务能跑但存证一条不写——会产出"全部 0 变化"的假绿灯。这次统一用标准起线脚本重启后才开跑，这一点已写进日志与任务卡。
