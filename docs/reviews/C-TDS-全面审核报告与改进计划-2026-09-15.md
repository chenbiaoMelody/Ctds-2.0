## 一、总体结论

> **项目制度执行力与代码工程质量处于"良好"水平（综合约 8/10），C-1.1 主体入驻链路已具备可验收的业务完整度；但"质量度量门禁（覆盖率/变异/静态扫描）全部未接入 + 门禁脚本本身在常见开发状态下崩溃 + 前端存在偶发红灯用例"三条同时成立，意味着当前"全绿"结论无法被机器复现——这是本轮审核唯一的系统性风险，建议列为最高优先级处理，处理完毕再恢复功能开发节奏。**

关键判断（供编排师取舍）：

1. **进度形态是"功能超前、质量基建滞后"**：按 WBS（W1 = 2026-09-07）今天为 W2 第 2 天，基建期（W1–W3）尚未结束，但功能开发 3.1.1~3.1.6 已全部完成并验收通过。好处是 M1（W6 末）压力小；代价是章程 §4.2 的覆盖率/变异/复杂度/SAST/SCA 五项门禁被搁置在 PENDING，**功能越写越多，欠账的丈量基础越难补**。
2. **本项目"人不管代码"的前提成立，但"机器把关"这一环目前是半空的**：无 CI（`.github/`、`.gitlab-ci.yml` 均不存在），门禁是本地 PowerShell 脚本，靠"人记得跑"；而该脚本在有后端进程运行时会直接崩溃（本次实测 2/2 复现）。**绿灯当前实际依赖 AI 自述**，与章程"绿灯不失真"相冲突。
3. **安全边界有一处"文档声明 ≠ 实际形态"的偏差**（见 AUD-03）：服务端直接信任客户端明文身份头，而前端注释称"安全边界在后端鉴权"。演示环境可接受，但必须登记为已知风险并给出关闭条件，否则后续任何"临时对外演示"都可能变成 S0 事件。
4. **制度层执行质量是本项目的亮点**：58 份开发日志续点四要素 58/58 齐备；规格→设计→剧本版本联动有留痕；评审打回项有修复记录；分级规范与等保清单对"尚未落地"的管控项**诚实标注"待生效"而不虚报**——这些在同类项目中很少见，应当保护并延续。

## 五、问题清单

> 严重度口径：**S1** = 影响"可信结论/安全边界"，须本轮收口；**S2** = 影响质量保证体系完整性，须 1~2 周内收口；**S3** = 债务/一致性问题，可并入后续包。

### S1 —— 须本轮优先收口

**AUD-01 门禁脚本在常见开发状态下崩溃，且与"真红灯"不可区分**
- 证据：E1（两次复现）+ E13（8080 端口 java 进程持有 `logs/app.log`）。根因有二：① `secretsScan` 阶段对 `$RepoRoot` 全量递归读取（**未排除 `target/`、`logs/`、`frontend/dist`、`build-output/`**），实测扫描 23,000+ 文件，其中大量是构建/运行产物；② `$ErrorActionPreference = "Stop"` 下**单文件读取异常无兜底**，直接终止脚本，未走到报告生成。
- 影响：门禁不能在"边开发边验证"的常态下运行；退出码 1 与真红灯同形；无报告可定位。**"门禁无特批"的操作基础被削弱**。
- 建议：① `secretsExcludePaths` 增补 `target`、`**/target/**`、`logs`、`**/dist/**`；② 每个文件读取包 `try/catch`，异常记 `FAIL（文件被占用/不可读）` 并继续；③ 脚本级 `try/finally` 保证**报告必出**；④ 崩溃路径退出码改用 `2`（配置/环境错误），与红灯 `1` 区分；⑤ 补一条"脚本自身健康用例"（构造被占用文件仍应产出报告）。

**AUD-02 前端存在负载敏感的偶发红灯用例**
- 证据：E3 失败 → E5 单文件 18/18 通过（该用例 7.3s，阈值 30s）→ E4 全绿。用例 `router.spec.ts:120` 依赖 `vite-node` 首次转换 `QueueView` 懒加载模块，测试注释已自认"并行负载下可达数秒"。
- 影响：同一提交可产出"红/绿"两种结论；配合 AUD-01，会让"绿灯"彻底失去可证伪性。
- 建议：① 该用例改为**显式 import 预热**（`await import('../views/review/QueueView.vue')`）后再断言导航结果，消除对外部转换耗时的依赖；② 或在 vitest 配置对 `router.spec.ts` 设 `testTimeout` 与 `retry: 1`（**仅限该文件**，并在配置中写明理由）；③ 门禁报告对"首次失败、重试通过"的用例单独标注，禁止静默吞掉。

**AUD-03 身份信任边界与文档声明不一致（演示期可越权）**
- 证据：E12。`common-auth` 的 `HeaderStripFilter`（剥离入站 `X-Ctds-Subject/X-Ctds-Roles`）由 `GatewayAuthAutoConfiguration` 装配，属**网关侧 Reactive 过滤器**；servlet 服务（subject/example）只装配 `AuthContextFilter`——**它直接读取并信任客户端传来的身份头**。前端 `demoRole.ts` 允许任意浏览器用户把角色切到 `admin`（→ `roles=applicant,reviewer`），从而获得 `subject.review`，可查看他人证照影像、审批入驻。而 `frontend/src/api/client.ts` 注释称"越权防护安全边界在后端鉴权"，`AuthAutoConfiguration` 的 WARN 仅覆盖 `ctds.auth.enabled=false` 场景。
- 影响：任何能访问 5173/8080 的人（含内网他人）都可越权；一旦按现形态做"对外临时演示"即升级为 S0 级事件。
- 建议：① **更正文档声明**（hifi/ADR-005 或 ADR-016 补记："V1.0 演示期服务直连信任客户端身份头，安全边界依赖网络隔离 + 3.5.2 网关 + 3.9.1 真实令牌"）；② 本机演示期间强制**仅回环地址**（`server.address=127.0.0.1`）并写入演示前置清单；③ 在风险登记册登记"身份头可伪造"，关闭条件 = 3.5.2 网关上线 + 3.9.1 令牌；④ 长期在 `common-auth` 增补一条"服务侧未见网关注入标记即拒绝"的开关（生产 profile 默认开启）。

### S2 —— 须 1~2 周内收口

**AUD-04 跨仓储的多写操作缺事务边界，存在"半成品档案"风险**
- 证据：E11 + 代码审读。`@Transactional` 只标在仓储单方法（`SubjectJdbcRepository.create/resubmit/appendTransition/nextDailySeq`、`CertificationJdbcRepository.replaceMaterial/updateConfirmation/appendVerification`），应用服务层无事务。因此：
  - `CertificationService.verifyLegalPerson` 通过路径 = `appendVerification(PASS)`（事务 A）→ `statusService.transition(...)`（事务 B）；若 B 因乐观门槛/DB 异常失败，**PASS 留痕已提交而主体仍停留"待认证"**，且该记录 `counted=false` 不占用当日失败额度 → 用户可无限重试，档案与状态不一致。
  - `uploadLicense` 同理：材料落库成功、`appendVerification` 失败 → 影像在库而调用留痕缺失。
- 影响：违反规格"不产生半成品档案"要求；对账/审计口径失真。
- 建议：在应用服务（use case）方法上加 `@Transactional`，使同一业务动作的多次仓储写加入同一事务（Spring 默认 REQUIRED 传播即可）；补 2 条回归用例（异常注入使第二步失败 → 断言无残留）。**须立任务卡**，不在本次审核范围内改动。

**AUD-05 法人身份证号校验存在放行缺口**
- 证据：`CertificationService.requireIdChecksum`（第 437~454 行）对**长度 ≠ 18 直接 return**，无任何格式校验；注释写"15 位旧格式只做格式校验"但该分支并不存在。→ 长度 3、20 等任意字符串可直送认证渠道。
- 影响：与 WBS-3.1.3 hifi B6"证件号校验位合法"的声明不符；也给模拟渠道之外的未来真实渠道留下脏输入。
- 建议：补"18 位（校验位）或 15 位（纯数字、出生日期合法）"两分支校验 + 边界用例；与 C-1.1 V1.2 的自然邻接项（电话格式）**合并立卡**更经济——但注意规格未定义 15 位口径，须随变更单补规格条款。

**AUD-06 覆盖率与变异两个章程硬门禁未接入，达标声明无法机器复现**
- 证据：`scripts/gates/gates-config.json` 中 `coverage / mutationTest / duplication / complexity / sast / dependencyScan` 全为 `enabled:false`（PENDING）；gate 报告长期 `PASS=9 FAIL=0 PENDING=8`。3.1.6 声称的"subject 98.0% / std 93.7% / crypto 93.0% / auth 91.3% 行覆盖"来自 **JaCoCo CLI 临时注入**，"红锚突变两轮全命中"为**人工抽验**。
- 影响：章程 §4.2（核心 ≥80%、整体 ≥70%、变异杀除率 ≥60%、圈复杂度 >15 打回、新增重复行=0）**当前无自动证据链**；随功能包增多，补测成本指数上升。
- 建议：按"工具链变更走 ADR/白名单流程"（章程 §3）立卡，一次性接入 JaCoCo + PIT + PMD-CPD + Semgrep + OWASP DC，把 5 项阈值变为门禁硬失败；在接入前，**门禁报告须显式声明"覆盖率/变异未度量"**，禁止在交付说明里以"达标"措辞表述。

**AUD-07 门禁非强制：无 CI、无服务端拦截**
- 证据：仓库无 `.github/`、无 `.gitlab-ci.yml`；WBS 2.2.2 的"CI 流水线"实际为"CI 无关的本地脚本"（README 已声明 D-3 切换预留）。唯一约束是会话纪律。
- 影响：门禁是否执行不可验证；历史上（E3/E4 同一提交两种结果）已出现结论漂移。
- 建议：最小接入即可（PR/push 触发执行 `run-gates.ps1` 并检查退出码），或在过渡期要求开发日志**附门禁报告文件路径**（`scripts/gates/reports/` 不入库，故建议门禁报告改为入 `build-output/` 或摘要入日志正文）。
