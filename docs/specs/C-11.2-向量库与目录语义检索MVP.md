## 1. 用户故事

作为**已入驻的数据需求方**，我希望在统一目录里**按意思找数据**：输入"金融风控"能优先看到名称、简介或语义标签相关的已上架产品，而不是只命中完全相同的关键词；同时作为**平台实施方**，我希望向量检索能力落在一个**可替换的底座**上——V1.0 用现有 MySQL 完成最小可用版本，不新增中间件、不调用外部模型、不产生费用，未来数据量触顶时可平滑切换到 pgvector/Milvus。本规格只覆盖 **P0-AI 底座预留的向量检索**；RAG/重排/生成/引用溯源与知识库管理归 V1.5 C-11.2 P1。

## 2. 行为清单（业务语言）

### 行为 1：向量化与向量存储抽象（B1）

**业务规则**

1. 平台提供**统一的向量化抽象**与**统一的向量存储抽象**：任何文本（产品名、简介、语义标签、用户检索词）经同一向量化器转成固定维度的向量；向量按产品标识持久化，供检索复用。
2. V1.0 的向量化 = **本地确定性算法**（Q3-A）：不调用任何外部模型/API、不需要密钥、不产生费用；同一文本在任何实例、任何时间得到同一向量；向量维度固定。
3. V1.0 的向量存储 = **MySQL 8 缓存表**（Q2-A）：向量随产品标识、源文本哈希、维度持久化；不新增 PostgreSQL/pgvector/Milvus 等中间件；`VectorStore` 抽象保留未来新增适配器即可切换的路径（ADR-003 §5）。
4. **诚实边界**：本地确定性向量不是真实语义模型——它能打通"向量化→存储→相似度检索"全链路，但对同义词、深层语义的识别能力有限；本 MVP **不承诺** PRD :263 的"目录语义检索 Top5 命中率 ≥90%"上线指标。

**验收标准（Given/When/Then）**

- Given 同一段文本，When 经两个独立的向量化器实例处理，Then 得到逐元素相同的向量且维度固定；
- Given 一段无有效词元的文本（如纯标点），When 向量化，Then 得到零向量，检索端返回空结果（不退化为全量返回）；
- Given V1.0 交付物，When 在断网环境运行全部测试，Then 全部通过，且模块依赖清单中无 HTTP 客户端/模型 SDK、仓库零真实密钥；
- Given 源文本变更，When 计算源文本哈希，Then 哈希值变化并触发该产品向量重算。

### 行为 2：索引范围与刷新（B2）

**业务规则**

1. **索引范围**：仅**已上架（LISTED）产品**进入语义检索候选；索引文本 = 产品名 + 产品简介 + 来源资源的语义标签（仅目录元数据，不含资源本体、不含敏感原文）。
2. **刷新方式**：检索时对"缺失 / 源文本哈希不一致 / 维度不一致"的向量**惰性重算并回写缓存**；不改动上下架、注销、产品变更等既有写面（Q5-A）。
3. **下架零泄漏**：语义检索结果**恒按产品当前状态 LISTED 硬过滤**；产品下架/注销后，即使缓存行仍在，也不得出现在结果中。
4. **变更可感知**：产品简介或来源资源语义标签变化后，下一次检索应按新文本向量化结果排序（产品名不可变口径不破）。
5. 查询文本不写日志；索引与检索只使用目录元数据，不读取资源本体。

**验收标准（Given/When/Then）**

- Given 一个已上架产品，When 执行语义检索，Then 该产品可出现在结果中；
- Given 一个未上架/已下架/已注销产品，When 执行语义检索，Then 结果中不出现该产品（即使其向量缓存存在）；
- Given 一个已上架产品，When 其简介从"农业气象"改为"金融风控"后再次检索"金融风控"，Then 该产品进入更靠前位置；
- Given 一个来源资源语义标签含"风控"的产品，When 用"风控"检索，Then 该产品可被命中（即使名称/简介不含"风控"）；
- Given 一次语义检索，When 检查数据写入，Then 不产生业务留痕/审计记录（向量缓存回写除外），不读取资源本体。

### 行为 3：语义检索端点（B3）

**业务规则**

1. **端点**：`GET /api/v1/catalog/semantic-search`（3.3.4 hifi §9-4 建议形态定稿）；认证 + 功能权限 `catalog.read` + **ADMITTED 资格门槛**（与 R6 同口径同文案，防枚举）。
2. **参数**：`q` 必填（trim 后 1~64 字符，语义检索词）；`categoryCode` 可选（须为类目树内节点，过滤含子树）；`pageNum` / `pageSize` 可选（ADR-005 分页规范，默认 1/10，上限 100）。
3. **结果范围**：恒仅含当前已上架产品；响应复用 R6 的 `CatalogProductView` 字段集与分页结构——**不暴露相似度分数、不暴露 status**；"检索 ≠ 可访问"口径同效（仅目录元数据，不含资源本体）。
4. **排序**：按向量相似度降序；同分时按上架时间降序；仍同则按产品 id 降序（稳定、可复现）。V1.0 **不设相似度阈值**：`total` = 满足范围/分类条件的候选产品数，按相似度排序后分页；阈值/截断策略归 V1.5。
5. **异常**：`q` 为空/纯空白/超长、`categoryCode` 不存在 → 统一参数错误 `1007C0013`（400）；未认证 → 401；缺功能权限 → 403；未入驻 → `1007C0006`（403）；不新增错误码、权限点。
6. 纯标点等无有效词元的检索词 → **空结果页（200，total=0）**，不报错、不全量返回。

**验收标准（Given/When/Then）**

- Given 已入驻且持 `catalog.read` 的主体，When 检索"金融风控"，Then 相关产品按相似度排序返回，Top-N 中出现名称/简介/语义标签相关的产品；
- Given 同一检索，When 检查响应，Then 字段集与 R6 完全一致（无 score、无 status），分页字段（list/total/pageNum/pageSize/totalPages）齐备；
- Given 分类 `finance` 含子类，When 带 `categoryCode=finance` 检索，Then 仅父类目及子树产品入选；
- Given 未入驻主体 / 无 `catalog.read` 权限 / 未认证，When 检索，Then 分别得到统一 403 未入驻文案 / 403 / 401，且零业务留痕；
- Given 空的 `q`、超 64 字符的 `q`、不存在的类目码，When 检索，Then 一律 400 + `1007C0013`；
- Given `pageNum` / `pageSize` 越界，When 检索，Then 按平台分页规范拒绝（`1000C0001`）。

### 行为 4：既有面零变化与零新增构件（B4）

**业务规则**

1. R6 关键词检索（`GET /api/v1/data-products`）行为**零变化**；既有 21 个 catalog 测试文件**零改动**；
2. **零新增外部构件/依赖**；**零新增服务、端口、网关路由**；**零门禁配置改动**；**零新权限点、错误码**；前端零改动；
3. 数据库迁移**仅新增 V5**（`product_embedding` 表），V1~V4 既有脚本与表结构零改动；表只作向量缓存，无业务外键；
4. 既有目录读写面的鉴权、ADMITTED、防枚举、检索 ≠ 可访问口径全部保持；向量缓存回写不产生业务留痕。

**验收标准（Given/When/Then）**

- Given 既有 R6 检索测试，When 运行，Then 全部通过且测试文件零改动；
- Given 本卡交付 diff，When 核对改动面，Then 仅新模块、根 pom 登记、catalog 语义检索链、V5 迁移与测试/文档，无其他既有文件改动；
- Given 全仓门禁，When 单发运行，Then GREEN 且 ConfigSha256 与基线逐字一致、coverage overall 不劣于 92.36%；
- Given 全库检索与门禁 secretsScan，When 检查密钥，Then 零真实密钥、零外部调用配置。

### 行为 5：向量库选型 POC 与性能（B5）

**业务规则**

1. 交付 **向量库选型 POC 对比**（MySQL 适配器 / PostgreSQL+pgvector / Milvus：运维复杂度、规模上限、演示资源、性能、信通院生态贴合），并记录选择 MySQL 首版适配器的理由与未来切换路径（ADR-003 §5）。
2. 在演示规模（1k / 10k 向量）上记录 Top-10 检索耗时（P50/P95/max）；10k 规模 P95 目标 ≤500ms（沿用目录检索性能指标口径），容器内单机、串行、资格门桩口径。
3. **诚实边界**：MySQL + Java 余弦为 O(n) 扫描，非生产级向量数据库；基准仅演示规模；正式并发压测与生产容量归 WBS-4.2.1 / V1.5；首查需填充缓存（冷启动成本须记录）。

**验收标准（Given/When/Then）**

- Given 1k/10k 演示数据与已填充缓存，When 运行基准，Then 输出 P50/P95/max 与目标判定，结果落盘且数字进入业务可读交付说明；
- Given 基准结果，When 解读，Then 明确标注"容器内单机、串行、Mock 资格门、无并发加压"边界，不宣称生产性能；
- Given 未来需切换 pgvector/Milvus，When 实现新适配器，Then 业务检索代码与端点契约无需改动（以 `VectorStore` 抽象与 POC 对比为路径证明）。

## 5. 边界声明

1. **能力边界**：本 MVP 的"语义"= 本地确定性向量的相似度排序，不是真实语义模型；同义词/深层语义能力有限，不得宣称达到 PRD :263 的 Top5 ≥90% 上线指标；
2. **介质边界**：MySQL 8 + Java 余弦为演示规模实现，非生产级向量数据库；数据规模/性能触顶时按 ADR-003 §5 新增 pgvector/Milvus 适配器切换；
3. **架构口径**：Q2-A 已确认 MySQL 首版适配器；ADR-003 §2.2/§3 的"PostgreSQL/pgvector 首版实现"由 ADR-003 增补勘误节承接（定稿确认时一并批准，不改历史原文）；
4. **索引边界**：仅目录元数据（产品名/简介/语义标签），不含资源本体与敏感原文；下架/注销产品即使缓存仍在也不出结果；缓存行不做主动清理（演示规模可接受，未来适配器规范化）；
5. **网关边界**：`/api/v1/catalog/**` 在网关无路由是**存量缺口**（存量 `/catalog/categories` 等同样如此），本卡零网关改动；验收直连 catalog 8084，未来网关暴露另立包；
6. **下游消费方**：3.10.3（语义检索非模型调用，无审计挂点）/ 3.10.4（本卡零配置键）/ V1.5 C-11.2（真实 embedding 适配器、pgvector/Milvus 适配器、RAG/重排/生成）/ 前端（未来界面经 Vite 代理调用本端点）。
