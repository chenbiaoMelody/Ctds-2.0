## 1. 用户故事

作为**已入驻的主体（企业 / 机构 / 政府部门）**，我希望**按场景创建一个逻辑空间**并设定参与方范围与可见性（例如"普惠金融空间""医疗验证空间"），以便在自己的场景域内组织协作，而不是把不同场景的参与方混在同一池子里。

作为**空间的所有者 / 管理员**，我希望**管理本空间成员的准入与退出、配置成员角色**，使只有经过同意的主体才能进入空间、并且各成员只能行使被授予的权限——以保证"谁在空间里、能做什么"清晰可查。

作为**空间所有者与平台运营方**，我希望**空间之间的数据与策略在逻辑上相互隔离、空间级策略从平台级策略继承且覆盖可管可查**，使跨场景的越权访问被一律拒绝、且下级的策略调整不会悄悄放宽上级的安全要求——以守住"隔离是底线、策略不降级"的治理原则。

## 2. 术语与角色

| 术语 / 角色 | 说明 |
| --- | --- |
| **逻辑空间（空间）** | 在物理平台上按场景隔离的虚拟数据流通域（PRD 行 232）；本规格中"空间"即"逻辑空间"，是成员、策略与（后续 C-3/C-4 的）数据资源与合约的**归属容器** |
| **主体** | 已完成注册与实名认证并**已入驻（ADMITTED）**的企业 / 机构 / 政府部门（C-1.1）；主体编号即其平台内唯一标识（对齐 C-1.1 术语） |
| **空间所有者（owner）** | 创建空间的主体；对空间拥有最高权限，唯一且**不可空缺**（行为 5 保护） |
| **空间管理员（admin）** | 由所有者授予、可管理成员与空间配置的成员角色（行为 4） |
| **空间成员（member）** | 经准入进入空间的参与方（行为 3），可在空间内行使成员权限（具体资源动作随 C-3.x / C-4.x 定义） |
| **平台运营方** | 平台侧治理角色：可冻结 / 解散空间、查看全部空间的治理信息（行为 2、7） |
| **参与方范围** | 空间对外接纳成员的口径：公开 / 邀请制 / 审批制（§7 Q2，已裁决采 A） |
| **可见性** | 空间本身在平台内的可见程度（公开可见可被检索申请 / 不公开仅成员可见）（§7 Q1、Q2） |
| **策略继承** | 平台级策略 → 空间级策略的默认继承关系；下级可覆盖但**不得放宽**上级（行为 7） |
| **红线（限制性条款）** | 上级策略中标记为不可放宽的限制项；下级覆盖若放宽即被拒绝（行为 7 规则 3） |
| **留痕四要素** | 本规格指"**谁 / 何时 / 对象 / 动作**"四项业务要素，只记业务要素、不含敏感原文；与 C-1.1 状态流转四要素（前状态/后状态/触发方/时间）、C-1.2 吊销五要素（含理由）为**同源方法、各域字段集自定义**（评审补正注记，防跨域混用同一字段清单） |

## 3. 行为清单（业务语言）

> **口径说明**：每条行为的"验收标准"即剧本步骤的判定依据；「（§7 Qx，已裁决采 A）」即该条依赖的决策点**裁决口径落点**（2026-09-25 编排师确认，沿 C-1.2 规格先例）。

### 行为 1：空间创建与要素设定（C-2.1）

**规则**

1. **资格门槛**：只有**已入驻（ADMITTED）**的主体可创建空间；创建者自动成为该空间的**所有者（owner）**；未入驻主体（申请中 / 待审核 / 已驳回 / 已撤销）一律拒绝，且拒绝口径**不区分**"主体不存在"与"主体未入驻"（防枚举，对齐 C-1.1 出站口径）。
2. **要素**：创建时须提供——空间名称、**场景类型**（如普惠金融 / 医疗验证 / 其他，取值口径见 §7 Q1）、**参与方范围**（§7 Q2，已裁决采 A）、**可见性**（公开 / 不公开）；可选项（如空间简介、生效期）随 3.2.2 数据模型落定。
3. **命名唯一性与长度门槛**：同一所有者的空间名称**唯一**（活跃空间的名称唯一性为"同一所有者"口径）；名称为空或超长一律拒绝并给出业务文案；名称中的控制字符与首尾空白归一化后判定（复用主体服务既有归一化口径）；**已解散空间的名称锁定为全平台口径**（任何主体不得再以该名称创建空间，见行为 2 规则 4——评审补正澄清，Q4 否决备选 C"同名不同空间混淆历史"的同义落地）。
4. **留痕（四要素）**：创建动作记录"谁（创建者主体）/ 何时 / 对哪个空间 / 做了什么"，且留痕**不含**任何敏感原文（对齐 C-1.1 / C-1.2 留痕口径）。
5. **幂等**：同一创建请求重复提交（同请求标识）只产生一个空间，重复请求返回首次结果（复用 `common` 幂等组件，ADR-007）。
6. **初始状态**：创建成功后空间处于"**已创建未启用**"（§7 Q4 状态机，已裁决采 A）；未启用空间不可接纳成员、不生效策略（行为 3、7）。

**验收标准**

- **GIVEN** 一个已入驻主体；**WHEN** 提交"名称 + 场景类型 + 参与方范围 + 可见性"完整的创建请求；**THEN** 创建成功、创建者成为所有者、空间进入初始状态，且创建留痕四要素齐备。
- **GIVEN** 一个未入驻（如待审核）主体；**WHEN** 尝试创建空间；**THEN** 被拒绝，提示为统一业务文案（不暴露该主体是否存在的差异）。
- **GIVEN** 同一所有者已有名为"普惠金融空间"的空间；**WHEN** 再次以同名创建；**THEN** 被拒绝；使用其它名称则成功。
- **GIVEN** 一个已存在的空间名称（同一所有者）；**WHEN** 以含首尾空白或控制字符的同一名称提交创建；**THEN** 归一化后判定为同名、创建被拒绝（空白与控制字符差异不产生新空间）（评审补正：行为 1 规则 3 归一化要求的标准化）。
- **GIVEN** 一次已成功的创建请求；**WHEN** 以同一请求标识重复提交；**THEN** 空间数量不变、返回首次结果（幂等）。

### 行为 2：空间生命周期（启用 / 冻结 / 解散）（C-2.1）

**规则**

1. **状态机**：`已创建（CREATED，未启用）→ 已启用（ACTIVE）⇄ 已冻结（FROZEN）`；**任一非终态（含未启用）均可解散**进入 `已解散（DISSOLVED）`（§7 Q4，已裁决采 A）；**冻结可恢复**（回到已启用），**解散不可逆**（终态）（评审补正：状态机完备化——明确"未启用可解散"与"冻结⇄启用"双向，与原"冻结可恢复、解散不可逆"口径一致，无放宽）。
2. **启用前提**：空间至少具备"名称 + 参与方范围 + 可见性"完整要素且所有者主体仍为 ADMITTED；启用后空间方可接纳成员、策略开始生效。
3. **冻结**：所有者 / 管理员或**平台运营方**可冻结；冻结期间**拒绝新成员准入与新增资源**，既有成员的读取是否受限随 3.2.4 设计（本规格只定"不得放宽"底线：冻结不解除任何限制）。
4. **解散**：仅所有者或平台运营方可发起，**不可逆**；发起时**须二次确认防误操作**（沿 C-1.2 吊销二次确认先例——评审补正）；解散后空间不再接纳成员、策略归档不可变，历史留痕保留可追溯（对齐 C-1.2 吊销"不可逆 + 留痕保留"口径）；**解散后空间名称不可复用**（§7 Q4，已裁决采 A；评审补正澄清：不可复用为**全平台**口径——任何主体不得再以该名称创建空间，避免跨主体"同名不同空间"混淆历史；活跃空间名称唯一性仍按行为 1 规则 3 同一所有者口径）。
5. **超权限拒绝**：非所有者 / 非管理员 / 非平台运营方对上述动作一律拒绝（行为 4 权限面）。
6. **留痕**：每次状态变更留痕四要素，含"从何状态 → 到何状态"与操作者。

**验收标准**

- **GIVEN** 一个刚创建的空间；**WHEN** 所有者启用；**THEN** 进入"已启用"，此后可接纳成员。
- **GIVEN** 一个已启用空间；**WHEN** 所有者冻结；**THEN** 进入"已冻结"，新成员准入被拒绝；**AND WHEN** 所有者恢复；**THEN** 回到"已启用"。
- **GIVEN** 一个已启用空间；**WHEN** 所有者解散；**THEN** 进入"已解散"且**不能再回到其它状态**（再尝试启用 / 冻结一律拒绝）；空间名称不可再被创建使用。
- **GIVEN** 一个空间；**WHEN** 一个**非成员**主体或**成员（非管理员）**尝试冻结 / 解散；**THEN** 被拒绝且记录拒绝留痕。

### 行为 3：成员准入（邀请 / 审批）（C-2.2）

**规则**

1. **资格门槛**：被准入主体须为 **ADMITTED**；未入驻主体不能被准入（错在提交时即拒绝，不区分"是否存在"）。
2. **准入形态由"参与方范围"决定**（§7 Q2，已裁决采 A）：
   - **公开**：主体可自助提交加入申请 → 空间管理员 / 所有者审批通过后成为成员；
   - **邀请制**：由所有者 / 管理员发出邀请 → **被邀方确认**后成为成员（未确认的邀请不产生成员关系）；
   - **审批制**：与公开同为"申请 + 审批"，差异在**空间可见性**（审批制空间不公开出现在检索 / 列表中）。
3. **空间状态门槛**：空间处于"已创建未启用"或"已冻结"或"已解散"时，**一律拒绝**准入动作（含邀请与确认），业务码区分"空间不可接纳成员"与"主体未入驻"。
4. **重复准入不产生重复成员**：已是成员者再次被邀请 / 申请→返回既有成员关系（幂等，不新增行）。
5. **留痕**：申请 / 邀请 / 确认 / 审批通过与拒绝各留痕四要素；拒绝须记录理由（业务文案）。

**验收标准**

- **GIVEN** 邀请制空间；**WHEN** 管理员邀请一个 ADMITTED 主体且该主体确认；**THEN** 该主体成为成员（成员数 +1）。
- **GIVEN** 邀请制空间；**WHEN** 邀请了但被邀方**未确认**；**THEN** 成员列表**不含**该主体（不产生成员关系）。
- **GIVEN** 公开 / 审批制空间；**WHEN** 一个 ADMITTED 主体提交加入申请；**THEN** 处于"待审批"而非直接成为成员；管理员批准后成为成员。
- **GIVEN** 一个未入驻主体；**WHEN** 被邀请 / 提交申请；**THEN** 被拒绝并给出统一业务文案。
- **GIVEN** 一个已冻结 / 已解散空间；**WHEN** 发起任何准入动作；**THEN** 被拒绝（业务码表意"空间不可接纳成员"）。

### 行为 4：空间角色与权限边界（C-2.2）

**规则**

1. **角色集合**：`owner`（所有者，唯一）/ `admin`（空间管理员）/ `member`（成员）（§7 Q3，已裁决采 A；只读审计角色归 C-9 审计域，本规格不新增）。
2. **权限面（本规格定义到"动作级"）**：所有者与管理员可执行——空间配置变更、成员准入审批 / 邀请 / 移除、角色授予与收回、冻结；成员可执行——空间内**读取与使用**（具体资源动作随 C-3.x / C-4.x）。
3. **越权一律拒绝（服务端强制）**：非成员访问空间内资源、成员执行管理员动作、管理员执行"仅所有者"动作（解散、转让所有权）→ 一律拒绝；**拒绝判定在服务端**，界面隐藏不构成权限（对齐 C-1.1 "安全边界在后端"口径）。
4. **权限点命名复用 `common` 鉴权**（RBAC，2.4.5）：空间域权限点形如 `space.admin` / `space.member`（命名随 3.2.4 定稿）；角色与权限点的映射由 3.2.4 落地，本规格只固定"三档角色 + 动作级边界"。
5. **不得自我提权**：成员不能给自己授予 admin；管理员不能把他人提升为 owner 或把自己的角色改为 owner（所有权变更只归所有者本人发起，随 3.2.4 设计）。
6. **留痕**：角色授予 / 收回留痕四要素。

**验收标准**

- **GIVEN** 一个空间含 owner / admin / member 三类成员；**WHEN** member 尝试执行"邀请成员 / 审批通过 / 冻结"等管理员动作；**THEN** 一律被拒绝（逐动作断言），并记录拒绝留痕。
- **GIVEN** 同一空间；**WHEN** 一个**非成员**主体直接请求空间内资源（绕过界面）；**THEN** 服务端拒绝（越权探测不因界面隐藏而放行）。
- **GIVEN** admin 成员；**WHEN** 尝试解散空间或把自己 / 他人改为 owner；**THEN** 被拒绝（仅所有者动作）。
- **GIVEN** member 成员；**WHEN** 尝试为自己授予 admin；**THEN** 被拒绝（不得自我提权）。
- **GIVEN** 一次成功的角色授予；**THEN** 留痕四要素齐备，且被授予者随后具备对应动作能力（正向对照）。

### 行为 5：成员退出与移除（C-2.2）

**规则**

1. **主动退出**：成员可退出空间（退出后不再能访问空间内资源）；**所有者不得退出**（须先转让所有权或解散空间，随 3.2.4 设计）。
2. **移除成员**：所有者 / 管理员可移除成员；**只能移除 member / admin**，不得移除所有者本人；移除须给出理由（业务文案）。
3. **唯一所有者保护**：任何情况下空间**不得出现"无所有者"**状态——移除 / 退出 / 角色变更均须校验"变更后仍存在且仅存在一个所有者"，违反即拒绝。
4. **状态门槛**：空间已冻结 / 已解散时可以**退出**（成员关系终止不受阻），但**不得新增成员或授予角色**（行为 3 / 4 的门槛一致）。
5. **留痕与可追溯**：退出 / 移除留痕四要素；被移除者此后对空间内资源的访问**立即失效**。

**验收标准**

- **GIVEN** 一个成员；**WHEN** 主动退出；**THEN** 成员列表不再包含该主体，且其后续访问被拒绝。
- **GIVEN** 一个成员；**WHEN** 管理员移除并填写理由；**THEN** 移除成功、留痕含理由，该主体访问立即失效。
- **GIVEN** 空间所有者；**WHEN** 尝试退出或被移除；**THEN** 被拒绝（唯一所有者保护）。
- **GIVEN** 已被冻结的空间；**WHEN** 成员申请退出；**THEN** 允许；**AND WHEN** 管理员尝试新增成员 / 授予角色；**THEN** 被拒绝。

### 行为 6：空间逻辑隔离（C-2.3）

**规则**

1. **默认拒绝**：除空间成员与平台运营方外，**任何主体对空间内资源与信息的访问一律拒绝**；空间之间**默认互不可见、互不可访问**。
2. **隔离在服务端强制**：隔离判定的唯一依据是服务端的成员与权限判定；**界面隐藏、参数篡改、直接调用接口**均不得绕过（越权探测口径同行为 4 规则 3）。
3. **可见性与可访问性分离**：可见性只影响"空间本身是否可被检索 / 申请"（公开可见 / 不公开），**不等于**空间内资源的可见性——公开空间内的资源仍只对成员开放（§7 Q6，已裁决采 A）。
4. **跨空间引用须显式授权**：一个空间的主体访问另一个空间的资源须以"成为该空间成员或获得该空间的显式授权"为前提（跨空间协作的合约 / 使用控制形态归 C-4.x，本规格只定"无授权即拒绝"）。
5. **隔离可核查**：平台须能给出"某主体对某空间资源的访问被拒"的**拒绝留痕**（谁 / 何时 / 目标 / 结果），供审计与 3.2.7 的跨空间隔离用例取证。

**验收标准**

- **GIVEN** 两个空间（A、B）及分属两空间的成员；**WHEN** A 的成员直接请求 B 的空间信息或空间内资源（绕过界面）；**THEN** 服务端一律拒绝，且产生拒绝留痕。
- **GIVEN** 一个公开可见的空间；**WHEN** 非成员检索到该空间并尝试读取其空间内资源；**THEN** 拒绝（可见性 ≠ 资源可访问性）。
- **GIVEN** 平台运营方；**WHEN** 查看空间治理信息；**THEN** 允许（治理例外唯一且留痕）。
- **GIVEN** 一次被拒绝的跨空间访问；**THEN** 拒绝留痕含"谁 / 何时 / 目标 / 结果"四要素且无数据原文。

### 行为 7：空间级策略继承与覆盖（C-2.3）

**规则**

1. **继承关系**：平台级策略为**默认**，空间级策略**默认继承**；未在空间级显式配置的条目按平台级执行。
2. **可覆盖但不得放宽**：空间级可覆盖平台级条目，**但若该条目为平台级"红线（限制性条款）"则不得放宽**——放宽（如扩大可见范围、延长留存、放松准入）的覆盖请求**一律拒绝**并给出业务文案；收紧方向的覆盖允许（对齐数据分类分级"就高"原则）。
3. **冲突取严**：多来源策略冲突时**取更严的一方**（限制性优先）；判定结果须可解释（记录"依据哪一条、取了哪一侧"）。
4. **可追溯**：策略配置与覆盖的每次变更留痕四要素，含"从何值 → 到何值"与操作者；**拒绝的覆盖请求同样留痕**。
5. **生命周期联动**：空间**已冻结**时策略不生效（拒绝新增接入，行为 2 规则 3）；空间**已解散**时策略**归档不可变**（保留可查，不得修改）。
6. **策略模型边界**：本规格只定义**继承与覆盖规则**；策略条目的字段与语言（可配置项范围、红线标记方式）随 **3.2.5 策略继承引擎**设计，并与 C-4.x 使用控制策略模型**对齐复用**（禁止两处各自定义策略模型）。

**验收标准**

- **GIVEN** 平台级策略中某条目为默认值且空间未配置；**WHEN** 读取空间有效策略；**THEN** 其值等于平台级默认值（继承生效）。
- **GIVEN** 平台级"红线"条目；**WHEN** 空间所有者提交**放宽**方向的覆盖；**THEN** 被拒绝且留痕（含拒绝理由）；**AND WHEN** 提交**收紧**方向的覆盖；**THEN** 成功生效。
- **GIVEN** 两个来源给出不同限制；**WHEN** 平台计算有效策略；**THEN** 取**更严**者，且说明依据来源。
- **GIVEN** 一个已冻结空间；**WHEN** 尝试修改其策略；**THEN** 被拒绝；**GIVEN** 一个已解散空间；**WHEN** 查看其策略；**THEN** 可查看但**不可修改**。

## 4. 非目标（本规格不做，边界划清）

1. **不做空间的数据模型与接口实现**（表结构、端点、迁移、错误码具体值）——归 3.2.2~3.2.4；本规格只定义业务行为与验收标准。
2. **不定义"策略"的本体**（策略条目集合、语言、引擎算法）——归 3.2.5；本规格只定义继承 / 覆盖 / 取严规则。
3. **不定义数据资源、数据产品与目录**（C-3.x）与**数字合约、使用控制执行**（C-4.x）——空间只是它们的归属容器，跨空间授权的合约形态归 C-4.x。
4. **不做网络级 / 容器级 / 存储级隔离**（"逻辑隔离"= 平台鉴权 + 查询过滤的强制口径）；网络边界与网关鉴权归 3.5.2 与部署层，本规格不承诺物理隔离。
5. **不做 AI 空间策略智能生成**（PRD V2.0 行 165 **C-2.4 = P2**）。
6. **不做空间配额 / 计费 / 智能体调用配额**（C-12.2 域）。
7. **不做跨空间身份互认**（C-1.2 已含 DID 互认；空间之间的成员互认与联邦另议）。
8. **不新增错误码码值、库表、迁移、第三方依赖**——均归下游实施包并在其设计中留痕（本规格只**预留错误码段位**，见 §7 Q7）。

## 6. 边界声明

1. **演示期安全边界**：演示态服务仅本机可达（ADR-016 §2.7），空间域端点**不得对外暴露**；网关上线前，空间隔离的"网络层"部分不存在，隔离结论仅覆盖**应用层鉴权与查询过滤**（诚实边界）。
2. **权限判定的强制点**：一切隔离与权限结论以**服务端**为准；界面隐藏、前端路由守卫均**不构成**权限（与 C-1.1 "安全边界在后端"同口径）。
3. **留痕不含原文**：空间成员与策略留痕只记业务要素（谁 / 何时 / 对什么 / 做了什么），**不落**任何敏感原文与个人信息（对齐 C-1.1 留痕口径与数据分级规范）。
4. **主体资格口径唯一**：空间域不得自行判定"主体是否可参与"——一律以 C-1.1 的 ADMITTED 为准（避免第二套资格口径）。
5. **策略不降级是硬约束**：任何"放宽上级红线"的实现路径（含界面、接口、数据订正）都不允许；本规格行为 7 规则 2 的拒绝须**代码强制**并有反向探针。
6. **名称与术语**：空间域统一使用"逻辑空间 / 空间"，资源命名采用 `data-spaces`（§7 Q7，已裁决采 A）；不在本域引入"租户（tenant）"等第二套概念。
