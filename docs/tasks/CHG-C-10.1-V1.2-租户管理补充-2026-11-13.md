## 1. 动机（为什么要改）

**WBS 行 339 要求 3.9.3 做"租户隔离配置、租户生命周期管理"，但规格没有定义它要做什么。**

- 规格 V1.1 **非目标 4**（`:161`）只写"不做租户生命周期服务（开通/升级/退役自动化）——归 3.9.3"，即把该能力**转出规格**，却未在 B1~B8 中给出任何行为、规则或验收标准；
- 规格 **B4**（`:84-96`）只定义"V1.0 租户 = 部署单元、不做库内 `tenant_id`、业务隔离走逻辑空间"，其验收标准 B4-1~B4-4 已由 C-10.1 剧本 S2（7 步）承载；**B4 不包含生命周期**；
- 剧本 S2-1（操作路径说明）已预告"部署配置读面（3.9.3 落定）"，但无规格可依；
- 全仓 `docs/specs/*.md` 无第二处定义；`tenant_id` / 租户表 / 登录 / 会话在代码与配置**零命中**（2026-11-13 复核）。

**结论**：3.9.3 若直接立卡实施，只能"猜需求"。按原则 1（规格先行）与红线 4（规格冲突/缺口停止上报），2026-11-13 会话已停止并呈报三案；编排师裁定 **A = 先补规格（变更流程）**，本变更单即为该裁定的执行。

**本变更的口径底线**（不重开 3.9.1 已裁决项）：

1. **不引入库内租户维度**——Q1-A 不变；B9 的"租户管理"= **部署域配置 + 版本/状态管理**，配置由部署清单 / 配置文件承载，不建租户表、不加 `tenant_id`；
2. **不虚构多实例能力**——V1.0 单实例单部署域；"开通"= 首次部署基线，"升级"= 版本递增 + 滚动更新，"退役"= 只读封存、不删数据；**不提供在线生命周期 API**；
3. **不改变既有判定**——B1~B8 与 C-10.1 S1/S2 的步骤编号、业务判定一字不改；新增内容集中在 B9 + S3 幕。
