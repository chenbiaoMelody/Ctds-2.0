## 一、缺陷定性（业务可读）

**发生了什么**：合约"提案"接口有一个并发兜底测试——两个请求同时提交新版本，测试本意只验证"恰好一个成功、另一个被拒、版本记录不乱"。但测试额外钉死了"被拒的那一个必须返回'正在被其他操作修改'"这一种提示。真实并发下，被拒的请求有两种合法结局：①两个请求几乎同时读到旧版本，后提交的撞版本唯一键 → 提示"正在被其他操作修改"（409）；②后到的请求读到对方已提交的新版本 → 命中"同一方不能连续提案"门槛 → 提示"当前状态不允许该操作"（409）。两种都是正确的业务拒绝，谁先谁后由线程调度决定。测试把其中一种当成了唯一正确答案，于是全仓门禁约一半概率会红——与业务代码质量无关，是测试预期过窄。

**修复口径**：接受两种提示码（仍必须是 409、仍必须恰一成一败、版本行数不变），即台账 DB-96 建议列的"两态可辨"。业务代码零改动。
