## 一、范围与设计要点（立卡段）

- **业务目标一句话**：给统一目录装"按意思找数据"的能力——检索时不再只匹配字面关键词，而是按产品名、简介与语义标签的向量相似度排序；本卡在现有 MySQL 8 上落一个**达演示可用、可替换**的向量检索底座，未来数据量触顶时换 pgvector/Milvus 只新增适配器、不改业务代码（ADR-003 §5 可替换性口径）。
- **为什么现在做**：WBS 3.10 AI-0 底座预留是 V1.0 P0 承诺（PRD :291 三件套：模型网关 / 向量库与目录语义检索 / 护栏与 AI 审计），3.10.1 模型网关已闭环；3.3.4 统一目录与 R6 检索已交付且已登记语义检索预留契约（hifi §9-4），依赖满足、接口基线明确。
- **本卡第一风险是 ADR 口径差**：ADR-003 指定 PostgreSQL+pgvector，但平台主库是 MySQL 8（ADR-001 冻结），ADR-003"复用主库零新增组件"的理由不成立；必须在 Q2 先裁定，禁止在设计里私改架构口径。
- **第二风险是向量化来源**：V1.0 零预算/零外呼，真实 embedding API 不可用；本地确定性向量可打通全链但语义能力有限——这是诚实边界，不是可隐藏的实现细节。
- **体量控制**：新 common 模块 + catalog 集成 + 迁移 + 测试，预计 600~900 有效行；单批超 400 按 AGENTS §6 拆 2~3 批链式 PR（预案见"立卡定点核查⑦"）。
- **首动作（编码段新会话，定稿后）**：读本卡 + 规格 V1.0 + hifi V1.0 → 等编排师建分支/提交授权（分支 `feat/WBS-3.10.2-向量库与语义检索` 自 `e972cc2`）→ 红相 → 实现 → 绿相 → 门禁 → 评审 → 验收。
