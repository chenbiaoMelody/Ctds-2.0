## 一、范围与设计

- **做什么 / 不做什么**：见 lofi §二（三个交付面）与 §四（六条边界）；行为清单 / 接口契约表 / 边界值与异常行为见 hifi §1~§4。
- **业务目标一句话**：把"三个管理员各管各的、不能互相越界"从**规格与剧本里的纸面约定**变成**平台实际执行的权限映射**——三员角色真实生效、权限授予可追溯、`admin` 不再同时握着审计读面与授权权，且整套判定仍走原来那一个内核。
- **立卡实测的五个缺口**（本包存在理由，均有证据）：
  1. **三员角色串零命中**：`platform.sysadmin` / `platform.secadmin` / `platform.audadmin` 在 `*.{java,yml,yaml,ts,vue,sql,xml,properties,json}` 全仓无实现，仅文档文字（规格:203/:208、台账:155、任务卡 3.9.1:41）；B2 分立目前**只由剧本人工验收**保证。
  2. **`admin` 超权面与 Q2-A 相反**：实测 9 服务 `application.yml` 中 `admin` 同时持有 `evidence.governance`（审计读面，evidence:35）、`connector.review`（授权/核验写面，connector:29）、`kms.admin`（kms:45）及各域 governance 写面；B2-4「三类关键点两两不重叠」与 B8-R3 目前不成立。C-8.2 剧本监管档亦为 `admin`（:45）。
  3. **映射只有配置来源、无库表留痕**：`ConfigRolePermissionMapper` 解析 `ctds.auth.permissions.<角色>`（`AuthProperties.java:21-22`、各服务 yml）；B1-R3 指定 3.9.2 覆盖 `RolePermissionMapper` Bean 换库表、B1-R4 指定落库后由库表留痕承载（规格:47-48），当前均无实现。
  4. **两个权限点未分离**：健康总览与核验写面共用 `connector.review`（DB-120 ⑤）；`kms.admin` 与授权类审批同持（DB-120 ⑥、规格:195）；`connector.health.read` 零实现。
  5. **DB-120 六项无承接包**：台账:155 明写 ①⑤⑥ 归 3.9.2、② 归 3.9.2 / 收口批、③④ 归部署期 / V1.5；3.9.1 验收段（卡 3.9.1:76-77）记"DB-120 默认随 3.9.2 承接"。

**设计要点摘要（供快速表决）**

1. **判定内核零改动**：新增映射来源只覆盖 `RolePermissionMapper` Bean，`DefaultAccessControl` / `PermissionInterceptor` / `@RequirePermission` 语义逐字不变（规格边界 2，ADR-005 行 37）。
2. **三员分立以"权限点集合两两不重叠"落地**（Q4-A）：三员各持一类关键点，`kms.admin` 不与权限授予同持；账号级"同一自然人不得兼任"归部署期（规格:62/:193），本包不引入账号体系。
3. **`admin` 收权按 Q2-A 一次性执行、落地前不提前撤权**：撤除审计读面 / 授权类权限点 / 运维写面，保留治理读面与治理审批（规格:208 口径固化）；C-8.2 监管档切换为 `platform.audadmin` 持 `evidence.governance`（DB-120 ①，须 PO 批准）。
4. **映射变更必须可追溯**：授予/收回写库表留痕（变更人/时点/角色/权限点/前后值），B1-4 双向用例守。
5. **不做规格外的事**：不做登录 / 令牌签发 / 库内 `tenant_id` / 租户生命周期 / 指标接入 / 告警外发 / 角色管理界面（依次归部署期 V1.5、3.9.3、3.9.4、生产扩展点、3.9.5）。
